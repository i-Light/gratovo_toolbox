## What to test: `apps/desktop/e2e/find-search.spec.ts`

On example data (no fake Supabase: the app runs `unconfigured`), with the real Python process the
app starts (`services/pipeline/.venv`, which `pnpm test` creates through `uv run`; CI runs that
before the e2e step):

1. Open Find › Search. Paste three of the example keywords (`ai video editor review`,
   `claude code tutorial`, `ai agents explained`) plus a duplicate; see 3 added, 1 skipped, and
   three queued rows.
2. Start the search. See the headline go to Searching "…", the log fill, the first keyword finish
   with "found · kept" numbers, and kept channels appear in the Kept list.
3. Pause while the second keyword runs (wait for its row to show "searching…" first). See the
   paused headline and "Resume at keyword 2" (or 3 if it finished first: accept either, by
   reading the number from the button).
4. Resume; see the run finish ("Finished · everything found is saved") and every row done.
5. Close the app and start it again on the same data folder: the queue, its done states, the
   found/kept numbers and the Kept list are still there.

Use the roles and names the screen gives (button names, `role="log"`, the list), not CSS. Wait on
what the person would see (`expect(...).toBeVisible()` / `toHaveText`), never on fixed sleeps. Give
the run steps generous timeouts (the example run takes a few seconds; CI is slower). Keep the
app's console free of errors, as the other specs check.

Then run it with `--repeat-each 3` to show it isn't flaky.

## Checks

`pnpm test:e2e` (Windows; it builds the app first). Report the pass counts of the normal run and
the `--repeat-each 3` run. Also `pnpm lint` and `pnpm typecheck`. Don't commit; the lead reviews
and commits. Don't touch `CLAUDE.md` or `docs/migration-plan.md`.
