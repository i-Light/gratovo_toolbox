## Goal

A signed-in member's local copy fills from the team's Supabase project and stays in step with it: creators, brands, deals, the team with roles, and the activity log. Every change the app makes that belongs on the server (your name, log lines, undo and redo, your notification switches, a creator's stage, a brand, a deal's step) is saved on this computer at once and reaches the server in order, even after a restart or a day offline. A stage change made on a stale value becomes a conflict you see and settle, never a silent overwrite. Nothing the server refuses is retried forever, and nothing unsent is overwritten by a pull. A teammate's change shows within a second or two (broadcast) and within 20 s at worst (catch-up); the rail shows who is online and on which screen. The open window updates without losing Undo, and the top bar tells the truth about whether changes have synced.

### Non-goals

Screens to edit creators, brands and deals (steps 4–8 use the write kinds built here; tests drive them through `invoke`). Compare-and-set for fields other than a creator's stage (`notes`, tags and the rest get their write kinds with their screens; the uploader already handles any whitelisted field). Mirroring the other 15 legacy tables (outreach, templates, campaigns and the rest: their steps). Any new screen beyond the sync state in the top bar, one line on the sign-in screen, toasts, and the conflict notifications (D17, D27). Encrypting `gratovo.db` (D20). Locking money in the database (Q1 recommends a follow-up). Keeping the old app working. The `search-1`, `first-1`, `mail-1`, `mail-2` gaps.

## Decisions

- **D1. One pull request** (owner, Q1). The tasks are cut small enough that each has one concern; the parallel plan below keeps the critical path to the engine (S9–S12) and the Realtime client (S27–S29).
- **D2. One engine in main, one pass at a time.** `apps/desktop/src/main/sync/`: a pass is (1) drop outbox rows of any other user, (2) drain the outbox, (3) re-fetch the rows the drain asked for (D10), (4) refresh the whole tables, (5) check the horizon, (6) seed the tombstone cursor on a first pull, (7) keyset-pull `channel_state`, `brands`, `deals`, `activity_log` in that order, (8) pull tombstones; then, if the drain sent anything, broadcast on `toolbox:sync` (D25). Single flight: a trigger during a pass runs one more pass after it. Triggers: start (once the session is restored), sign-in, a write (1 s after the last one), a broadcast from a teammate (1 s debounce), the 20 s catch-up tick, `sync:now`. Pass budget 2 min; an unfinished pull carries on next pass from its stored cursor. The engine uses the account's one `Rest`, and Realtime's `accessToken` uses the same `Session` (one single-flight `accessToken()`; a second refresher would end the session on a rotated token, CONTEXT risk 15). It never opens a second database connection.
- **D3. What is pulled.** Keyset: `channel_state` (cursor `updated_at`, key `channel_id`), `brands` and `deals` (`updated_at`, `id`), `activity_log` (`received_at`, `id`, D5). Whole each pass (tiny, and none has tombstones): `profiles`, `member_access`, `notification_switches` (RLS returns only your row), `edit_conflicts` where `mine_actor_id = me` and `resolved_at is null`. Tombstones only for `channel_state`, `brands`, `deals` (`table_name=in.(…)`). `sync_control` for the horizon. The other 15 legacy tables stay unpulled until their steps.
- **D4. Keyset pages and cursor precision.** Query: `select=<columns>&order=<cursor>.asc,<key>.asc&limit=<n>&or=(<cursor>.gt."<c>",and(<cursor>.eq."<c>",<key>.gt."<k>"))` (three-part for tombstones), every value double-quoted (`"` and `\` escaped) and the whole parameter `encodeURIComponent`ed, so a `+00:00` never turns into a space. The cursor is the **last row's raw text** from the server (µs, `+00:00`), stored in `_meta` `sync.cursor.<table>` as JSON `{ at, key }`; it never passes through `Date`. Page 500, halved on a timeout or 5xx down to 25 (`sync.page.<table>`), back up by doubling after 5 good pages; request timeout 45 s. A page whose last cursor equals the stored one stops that table for this pass and logs `pull.stalled`. Each page is applied in one `BEGIN IMMEDIATE` transaction with an `await` on `setImmediate` between pages, so IPC answers between them. Rows are written with `INSERT … ON CONFLICT(<key>) DO UPDATE SET …` over every pulled column, **not** `INSERT OR REPLACE`: that deletes the row first, changes its `rowid` (the frame's order) and would drop local-only columns. Timestamps stay server text in the mirror; comparisons go through `compareServerTime` (µs) or the local `activity_log.at_ms` (D11).
- **D5. `activity_log` gets a server receive time.** Its `at` is the writer's clock, so a member who was offline uploads lines with an `at` older than my cursor and a keyset on `at` never sees them. Additive column `received_at timestamptz not null default now()` and index `(received_at, id)`; the app pulls by it and never sends it. Existing rows all get the migration's time (one value; the `id` tie-break pages them). Why not an overlap window on `at`: any window can be outrun by a longer absence.
- **D6. Tombstones, the resurrection guard and the horizon.** **Seed:** on the first pull (no `sync.seeded`), before any data page, the tombstone cursor is set to the newest tombstone (`order=deleted_at.desc,table_name.desc,row_id.desc&limit=1`), or to `-infinity` when there is none; older deletions are of rows the data pull won't bring, so the first pull reads none of production's ~38k tombstones. **Apply:** `DELETE` the local row only when it has no pending outbox entry and its `updated_at` is older than `deleted_at` (`compareServerTime`), so a row re-created after its deletion survives. **Horizon:** each pass reads `sync_control.tombstones_purged_before`; if the stored tombstone cursor is older, every cursor resets, `sync.seeded` goes, and the next pull is a full one that marks every key it sees in a `TEMP` table; at its end, local rows of the three tables that weren't seen and have no pending entry are deleted. The outbox is never touched.
- **D7. The outbox of intent.** Local `_outbox(seq INTEGER PRIMARY KEY AUTOINCREMENT, user_id, kind, payload /* JSON */, target_table, target_key, created_at, attempts, last_code)`, plus `_outbox_dropped` (what the server refused). Kinds: `profile.name` `{ name }` → `PATCH profiles?id=eq.<me>` `{display_name}`; `activity.add` `{ row }` → `POST activity_log?on_conflict=id`, `Prefer: resolution=ignore-duplicates,return=minimal`, up to 200 consecutive rows per request; `notify.set` `{ switches }` → `POST notification_switches?on_conflict=profile_id`, `resolution=merge-duplicates`; `channel.edit` `{ channelId, field, base, next, label }` → `rpc/apply_channel_edit` with the six named parameters (`p_force: false`); `conflict.resolve` `{ id, resolution, value }` → `rpc/resolve_edit_conflict`; `brand.set` `{ id, name, sells, status }` → `POST brands?on_conflict=id`, `merge-duplicates`, only those columns; `deal.step` `{ id, step }` → `PATCH deals?id=eq.<id>` `{ flow_step }`. Rows are enqueued in the **same transaction** as the local write (D11), so a crash can't keep one without the other. Strict FIFO: the head is sent first, and a retryable failure stops the drain ("sending entry 7 after entry 6 failed would apply an edit on a state the server never reached", legacy uploader ~L113). Each row carries the user id; the engine sends only the session user's rows and deletes any other user's at the start of a pass. `updated_at` is never sent.
- **D8. Refusal rules, ported exactly.** From `isFinalUploadRefusal` (uploader L54-68): a PostgREST error with code `42501`, any `22…` or any `23…` → **drop** (move to `_outbox_dropped`, count it, toast once, D17, and re-fetch the target row, D10). Schema behind (`PGRST202`, `PGRST204`, `PGRST205`, `42883`, `42703`, `42P01`) → **retry**: a forgotten migration must not lose edits. HTTP 401 after Rest's one refresh, or an `AuthError` → **session**: stop the pass, keep the row. Offline, timeouts, 5xx, 429 and anything else → **retry**. A drop is the only data-loss path, so the app only builds payloads the server accepts (tests) and every drop is visible.
- **D9. Retries and "stuck".** After a failed pass the next one waits 30 s, 2 min, 10 min, then 30 min (legacy ladder); a good pass returns to the 20 s tick; `sync:now` runs at once and resets the ladder. The head's `attempts` grows once per pass that fails on it; at 4 the status says `stuck` (D17). Nothing is skipped past a stuck head.
- **D10. Unsent work is never overwritten** (CONTEXT risks 2, 9). (1) Drain before pull in the same pass. (2) The puller skips a pulled row whose `(table, key)` has a pending outbox row; the whole-table refresh writes back a pending `profile.name` and `notify.set` over what it read, and keeps a conflict hidden while its `conflict.resolve` is pending. (3) After a `conflict` outcome or a drop, the uploader records the target in `_meta` `sync.refetch` and the next step of the pass reads that row by key (`<key>=eq.<value>`) and writes it, or deletes it locally if the server has none, unless another entry for it is pending: the local value reverts to the server's, as the old app's comment promised. (4) The page adopts a new frame only while its persister is idle and its data hasn't changed since it asked (D16).
- **D11. Write intents and the log's shape.** In the live source each `data:write` runs a hook inside the batch's transaction (`onWrite`, Contracts). `me.name` → local write, then `profile.name` with the same cleaned name. `notify.set` → local write, then `notify.set`. `notification.read` → local only. `log.add` → a local row in the app's own shape (`action = 'note'`, `entity_type = 'app'`, `entity_label = text`, `detail = {"text": …}`, actor id, the actor's name and role from the local profile, `at` as ISO text) and `activity.add` with the same row; if that id already exists and is hidden by an undo (a redo), a **redo marker** instead. `log.remove` (an undo) → if the line's `activity.add` is still unsent, delete both; else keep the line and add an **undo marker**, enqueued as `activity.add`. Markers: a new UUID, `action = 'undo'` or `'redo'`, `entity_type = 'activity_log'`, `entity_id` = the line's id, `entity_label` = its text. The server only ever gets inserts (append-only, owner 2026-10-20). The frame hides markers and every line whose newest marker is an undo. The 364 existing lines (written by the old app) become text through core `logText(row)` (D14). Lines written locally by 3d-1/3d-2a (`entity_type = 'app'`, no `detail`) read their `action` as text and stay local. Local migration 3 adds `activity_log.at_ms` (backfilled), `received_at`, and indexes on `(at_ms DESC, id DESC)` and `(entity_type, entity_id)`; `newestLog` orders by `at_ms`, because ISO text with `Z` and with `+00:00` don't sort together. The new write kinds (D26) are intents too: `creator.stage` → local `creator_stage`, then `channel.edit` with `field: "creator_stage"`, `base` = the local **column** value before the write (null when never set, so a first edit isn't a false conflict), `label` = the handle; `brand.set` → local columns, then `brand.set`; `deal.step` → local `flow_step`, then `deal.step`; `conflict.resolve` → the local conflict marked resolved (and, for `mine`, the local stage set to mine), then `conflict.resolve` with `value` = the chosen side's value.
- **D12. The app's own columns win; the legacy fields are only a fallback.** The app writes `creator_stage`, `sells`, `status`, `flow_step` and nothing else of a row's legacy fields. Reading is unchanged from 3d-1: the app column when it holds a valid value, else derived from `vetting_status`/`pipeline_stage` or the deal's `stage`, so existing rows still show. `brands.sells`/`status`: null reads as `""` and `"found"`. Steps 4–9 may stop reading the legacy fields once every row has the app's column (a one-off backfill, not here: it would rewrite existing data).
- **D13. The frame stays inside the IPC limits** (CONTEXT risk 1; owner, Q4). `listMax` stays 5000. `listCreators` returns at most 5000: every creator a deal names first, then creators past `new` (`creator_stage` set or the legacy fields not `newlyFound`/`new`), then the most recently pulled; one SQL query with `LIMIT`, `primaryEmail` only for those rows. Notifications newest first with `LIMIT 5000`; brands and deals keep their cap (an over-cap table is cut, not a failed `frame:load`). `Frame.conflicts` ≤ 100. Measured in the contract suite: 20,000 `channel_state` rows give a frame that passes `frameSchema`, holds every deal's creator, and serialises under 2 MB. Step 5 replaces the palette's creator list with a search query and can lift the cap.
- **D14. Money can't leak through notifications or the log** (closes ADR 0011's consequence). Notifications: local column `notifications.money` plus a backstop, core `mentionsMoney(text)`; for a member without money, a notification of kind `money`, flagged `money`, or whose text or sub mentions money is dropped. Log lines: for a member without money, a line whose `field` is in core `moneyFields` (`brand_price`, `influencer_payout`, `budget`) or whose text mentions money is dropped from the frame. Conflicts carry no money field (only `creator_stage` is editable through the app). Dropping, not editing: a hidden line can't half-show an amount.
- **D15. Main-to-page events.** One Electron channel `gratovo:event` carrying `(name, payload)`. Names and schemas in `packages/ipc/src/events.ts`: `frame:changed` `{ parts }` (`team`, `me`, `creators`, `brands`, `deals`, `log`, `notify`, `conflicts`), `sync:status` (D17), `presence:changed` `{ members: [{ id, status, doing }] }` (≤ 50). Main validates every payload before sending and sends only to the app's own windows (the page URL check `isTrustedSender` uses); a bad payload is logged by name and dropped. The preload adds `on(name, listener) → unsubscribe`: one `ipcRenderer.on` per call, the listener gets the payload only (never the Electron event), unknown names are ignored, and it imports only types and constants (`bridge.ts`), so the sandboxed preload still bundles no zod. During a long pull `frame:changed` goes out at most once per 2 s and at the end of each table.
- **D16. The page adopts server data without writing it and without losing Undo.** `renderer/lib/live.ts` listens for `frame:changed`, waits for `persistenceIdle()`, notes the store's data, calls `frame:load`, and applies the answer only if the data is still the one it noted and the persister is still idle; otherwise it asks again at the next idle (at most once a second). Apply = `adoptServerData(recipe)` in `persist.ts`: sets an `adopting` flag, runs `store.bg(recipe)`, and the persister takes the result as its baseline with nothing written. `mergeServerData` replaces `team`, `conflicts`, `seesMoney`; replaces each creator, brand and deal by id except those with a change still queued in the persister (it can't be, while idle; the check is a guard); inserts log lines it hasn't got and removes teammates' lines that are gone (newest first, 50 kept); takes `myName` and `notify` only when `parts` names `me`/`notify`. `bg` applies the same recipe to every undo and redo step, so undoing an older change never removes a teammate's line or reverts a teammate's stage. `presence:changed` is adopted the same way, touching only `status`/`doing`. A changed account or access still reloads the window (3d-2a).
- **D17. The sync state is visible, minimally.** IPC `sync:status` and `sync:now` (`{}` → status) and the `sync:status` event. Status `{ state: "off" | "syncing" | "synced" | "offline" | "stuck", pending, refused, lastSyncedAt }`; `off` with no live source (unconfigured, signed out, waiting), where `pending` counts changes kept from a signed-out session (D18). UI: (1) the top bar's save chip keeps "Saving…"/"Saved"/"Not saved" for the local write and shows **"Not synced"** when changes wait and the state is `offline` or `stuck`; its tip says what is true ("Saved on this computer and synced 2 min ago", "Saved on this computer. 3 changes will sync when you're back online.", "Saved on this computer. A change keeps failing to sync; it will keep trying."). (2) A toast when `refused` grows: "The server refused a change" / "It stays on this computer only." (3) One quiet line on the sign-in screen when a signed-out copy holds unsent changes: "3 changes from your last session are waiting on this computer. Sign in to send them." The conflict notice is D27. All words in `renderer/strings.ts` or, for text main builds, `main/strings.ts`.
- **D18. Sign-out keeps unsent changes** (owner, Q3). The page waits for its persister as today, then calls `sync:now` once; then `auth:sign-out`. Main gives the drain up to 5 s more; if the outbox is empty it deletes `gratovo.db` as in 3d-2a. Otherwise it keeps the file with **only** `_outbox` and `_meta.account.user_id`: one transaction deletes every row of the mirror and local tables, `_outbox_dropped` and every other `_meta` key, then `VACUUM` and close. At start, a copy without a session is deleted unless it holds outbox rows. Signing back in as the same account keeps the file, pulls from scratch and sends the rows first. A server-ended session keeps unsent rows the same way. Signing in as someone else deletes them (logged with the count). Demotion to waiting deletes the copy. Realtime disconnects before any of this.
- **D19. The team refresh and the name PATCH fold into the engine.** `account/team-refresh.ts` becomes `sync/whole-tables.ts` (same columns and replace-in-one-transaction, plus `notification_switches` → local `notify`, plus `edit_conflicts`, plus D10's pending rule); `account/live-writes.ts` goes (the name is an outbox row). Sign-in still waits for the whole tables (not the keyset pull) before answering, so the first frame shows the team. **Changed behaviour:** offline, a rename now saves locally and shows "Saved" with the waiting tip, instead of "Not saved"; the 3d-2a e2e expectations change with it.
- **D20. `gratovo.db` stays unencrypted** (owner, Q2). It will hold ~15.6k creators' contacts. `node:sqlite` has no encryption, SQLCipher would bring back the native module ADR 0010 avoided, and encrypted columns would break the searches of steps 4–9. The file is in the Windows account's own profile and is deleted on sign-out (D18); `docs/setup.md` advises BitLocker on every team computer.
- **D21. Migration `20261022090000_sync_columns.sql` (additive).** `channel_state.creator_stage text` (check: null or one of the 11 `creatorStages`), `brands.sells text` (≤ 500 characters), `brands.status text` (≤ 40), `deals.flow_step smallint` (0 to 9, `DEAL_FLOW`), `activity_log.received_at` and its index (D5), and `public.notification_switches(profile_id uuid primary key references public.profiles(id) on delete cascade, switches jsonb not null default '{}' check (jsonb_typeof(switches) = 'object'), updated_at timestamptz not null default now())` with `trg_notification_switches_touch` (`touch_updated_at`), RLS on, policies `notification_switches_read` (select), `_insert`, `_update`, each `to authenticated` with `profile_id = (select auth.uid()) and (select public.is_authorized())`, no delete policy; grants: `revoke all … from anon`, `select, insert, update, delete` to `authenticated` (test_30's rule; no delete policy refuses deletes), all to `service_role`. Named constraints dropped and re-added; re-runs cleanly; the runner's pass after a `schema.sql` re-run leaves the same privileges. Rewrites no existing value (new columns start null; `received_at`'s constant default needs no table rewrite). The checks scan ~15.6k `channel_state` rows in well under a second.
- **D22. - **D26. The app's presence payload** (owner, Q5: not the old app's fields).
