# Plan: step 3d-2a, sign-in, roles and team keys

The first of two pull requests for step 3d-2 (owner, 2026-10-20). **3d-2a (this plan):** email and password sign-in with the session kept in the main process through `safeStorage`; the "waiting for access" state; agency roles (a list per person) and the "sees money" switch, stored apart from access; the main-process network allowlist; the team keys (the YouTube key in Supabase Vault behind a members-only function, R2 as short-lived signed links from an Edge Function); `docs/setup.md`; the additive Supabase migrations these need, and a local Supabase test job. **3d-2b (later, outlined at the end):** the sync engine and the other additive columns. Read `.router/CONTEXT.md` first (§2, §3, §4, §5, §7). Bash commands start with `export PATH="$HOME/.local/opt/node-v24.22.0-win-x64:$HOME/.local/bin:$PATH";`. **Never read `.env*` or `*.local.json` files** (this includes `apps/desktop/.env.local` and the legacy `data/.env`), and never read, print or handle a key value. No task touches the production Supabase project: that is the lead's rollout (R1), one step at a time with the owner's go.

Docs checked on 2026-10-20 for this plan: Supabase changelog (breaking changes 2025–2026: new public tables are no longer exposed to the Data API without explicit grants, enforced 2026-10-30; TLS cipher change 2026-11-10; legacy `anon`/`service_role` keys to be deprecated by the end of 2026), API keys (publishable `sb_publishable_…` keys are meant for desktop apps and go in the `apikey` header; secret keys never ship), Auth error codes and sessions (single-use refresh tokens, 10 s reuse window, reuse outside it ends the session; branch on the error code, not the message), Edge Functions auth and secrets (`verify_jwt` defaults to true and should stay on; default env `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEYS` (JSON, entry `default`), legacy `SUPABASE_ANON_KEY`; custom secrets can't start with `SUPABASE_`, are set in the dashboard or with `supabase secrets set`, and apply without a redeploy), Vault (`vault.create_secret(secret, name, description)`, read through `vault.decrypted_secrets`; anyone who can read the view reads the secrets), R2 presigned URLs (GET, HEAD, PUT, DELETE; 1 s to 7 days; region `auto`; host `https://<account>.r2.cloudflarestorage.com`; only the S3 API domain; treat as bearer tokens). Supabase CLI on npm: newest stable 2.121.0 (2026-10-14); **2.119.0** (2026-09-30) is the newest at least two weeks old. `aws4fetch` 1.0.20 is from 2024-08 and inactive.

## Goal

A team member opens the app, signs in with email and password, and lands in the app on their own account: their name, the team with each person's agency roles, and nothing that shows money unless they may see it. A new account whose access is still `unauthorized` sees a calm "waiting for access" screen instead of an empty app. The sign-in survives a restart, encrypted with the Windows account's key and never visible to the page. The main process talks only to the project's Supabase host. A signed-in member can get the YouTube key and short-lived R2 links from the server; no key ships in the app or the repository. The old app keeps working against the same project, because every migration only adds.

### Non-goals

The sync engine (pull, outbox, compare-and-set, tombstones, conflicts), Realtime, presence, main-to-page events, and the additive columns for creator stage, brand sells and status, deal flow step and per-person notification switches (all 3d-2b). Any UI to edit roles, "sees money" or access (step 9's Settings › Team; until then the owner's SQL in `docs/setup.md`). Locking money in the database (steps 10–11). Sign-up, password reset, magic links, "remember me" (the owner creates accounts in Supabase, as today). A consumer of the team keys (the pipeline, step 3e). Encrypting the SQLite file (3d-2b, when contact data first arrives). Prototype mode (3f). Rotating keys (A1, deferred by the owner). The `search-1`, `first-1`, `mail-1`, `mail-2` gaps.

## Decisions

- **G1. Plain `fetch` in main, no `@supabase/supabase-js`.** 3d-2a needs six calls: password grant, refresh grant, logout, a PostgREST select, a PostgREST RPC and a PATCH, plus one Function call. Each is a few lines over `fetch` (Node 24's global, inside Electron 44.9.0). Owning them means the session lives exactly where we put it (no storage adapter, no `localStorage` assumptions, no URL session detection, no background timers we don't control), every request goes through the allowlist by construction, and tests fake one function. Cost: we write the refresh logic (single flight, 60 s before expiry, back-off) and the error mapping; both are small and the server tests run them against real GoTrue. 3d-2b decides on Realtime (likely `@supabase/realtime-js` alone, given its transport option, or a small Phoenix client) when it builds presence. **No new runtime dependency in 3d-2a** (the SigV4 signer is ~100 lines over WebCrypto; `aws4fetch` is inactive since 2024 and would need an import map in Deno).
- **G2. Supabase config: the project URL and the publishable key, at build time.** SECURITY.md says non-secret config is passed at build time, never hard-coded in source; the old app compiled them in. electron-vite reads `MAIN_VITE_SUPABASE_URL` and `MAIN_VITE_SUPABASE_PUBLISHABLE_KEY` from the environment or `apps/desktop/.env.local` (already git-ignored by `.env.*`; the owner writes it once, `docs/setup.md` says how; sessions never open it). Release builds (3h) take them from GitHub Actions *variables* (not secrets: they are public) and must refuse to build without them. A pure reader (`main/supabase/config.ts`) checks them at start: URL `https://<20 lowercase letters/digits>.supabase.co` with no path; key must start `sb_publishable_`. It **refuses** `sb_secret_…` and anything shaped like a JWT (a legacy `anon` key is deprecated by Supabase, and a pasted `service_role` JWT must never be accepted), with a startup log line naming the problem but never the value. Missing config = **unconfigured**. **Test seam, unpackaged only** (like `GRATOVO_USER_DATA`): when `!app.isPackaged` and `GRATOVO_SUPABASE_URL` is set, it and `GRATOVO_SUPABASE_PUBLISHABLE_KEY` replace the built values; an empty URL means unconfigured; `http://127.0.0.1:<port>` is accepted there only. Packaged builds ignore the environment. Why not a first-run entry: every member would have to type a URL and key; why not a committed constant: the policy forbids it and gitleaks would rightly object.
- **G3. One network module; the page stays `connect-src 'self'`.** `main/net/network.ts` exports `createNetwork({ allowedOrigins, fetch })` with `request(url, init)`: parses the URL; refuses (throws `NetworkRefusedError`) unless its origin is exactly one of `allowedOrigins` (the project origin; `http://127.0.0.1:<port>` only through the G2 seam), it has no user name or password, and the scheme is https (or that seam); sets `redirect: "error"` so a redirect can't leave the host; applies a timeout (`AbortSignal.timeout`, default 30 s). It also exports `checkWebSocketUrl(url)` (wss on an allowed origin) for 3d-2b. **Enforced by lint:** an ESLint block for `apps/desktop/src/main/**` (except `net/network.ts` and tests) forbids the globals `fetch`, `WebSocket`, `XMLHttpRequest`, `EventSource` and imports of `node:http`, `node:https`, `node:net`, `node:tls`, `node:dgram`, `http`, `https`, `net`, `tls`, `undici`, and `net` from `electron`. Defence in depth for the page: `blockForeignRequests(session)` in `security.ts` cancels any session request whose URL isn't `app://gratovo/` (plus `devtools:` and, in dev only, the Vite server); Node's `fetch` in main doesn't pass through it, which is why the lint rule exists. R2 links are not allowlisted: in 3d-2a only the pipeline (3e, Python) will use them; if main ever fetches R2 it adds that origin here with a reason.
- **G4. The session lives in the secret store, refresh token only.** Secret name `supabase.session`, value JSON `{ userId, email, refreshToken }` (the access token stays in memory; a start costs one refresh, and nothing long-lived beyond the refresh token is on disk). `safeStorage` unavailable → sign-in answers `problem: "no-safe-storage"` and nothing is stored (the store already refuses; no plain-text fallback). No IPC channel ever returns a token, a password or a key; `auth:status` returns the account's own email only. Refresh: single flight, 60 s before `expires_at`, after a failed network attempt back off 30 s, 2 min, 10 min; the stored token is replaced atomically after every rotation. **Ends the session** only on Auth codes `refresh_token_not_found`, `refresh_token_already_used`, `session_not_found`, `session_expired`, `user_banned` (or a 400/401 from the token endpoint without a code); network errors, 5xx, 429 and `conflict` keep it. Error objects and logs carry the code and HTTP status only, never a body, token or password.
- **G5. Who sees what at start (`Account` in `main/account/`).** States: **unconfigured** (no G2 config: the example source, no sign-in UI; dev builds and the existing e2e tests), **signed-out** (the sign-in screen; no source open), **waiting** (session valid, own `profiles.role = 'unauthorized'`: the waiting screen; no source open), **signed-in** (the live source on `gratovo.db`, `me` = the user's id). With a stored session the app opens **offline-first**: the last known access is in the live database's `_meta` (`account.user_id`, `account.access`), so `frame:load` answers from the local copy at once and the network catches up behind it (refresh the token, then refresh the team). If the background check finds the session ended or the access dropped to `unauthorized`, main updates the state and **reloads the window**, and the page starts over from `auth:status` (no main-to-page events in 3d-2a; a reload also clears undo history, which must not cross accounts). On the **first** sign-in of an account the team refresh is awaited before `auth:sign-in` answers, so the first frame already shows the team. Why not keep example data when signed out: a real account and fixture data must never mix; example data comes back as owner-only prototype mode in 3f (ADR 0004), which will swap the account's source for the example one at run time, the same `Account.source()` seam.
- **G6. The live copy belongs to one account.** `_meta.account.user_id` names it. Signing in as someone else, or signing out, closes the live source and **deletes** `gratovo.db` (and `-wal`, `-shm`): it holds the team's data, which must not stay readable on disk after sign-out. In 3d-2a nothing in it is unsent except local-only notifications, device settings and log lines (none reaches a server until 3d-2b), so they go too; 3d-2b revisits this with the outbox (unsent rows survive, as in the old app).
- **G7. The team refresh (a stopgap until the 3d-2b pull).** `main/account/team-refresh.ts`: `GET /rest/v1/profiles?select=id,display_name,color,role,created_at,updated_at` and `GET /rest/v1/member_access?select=profile_id,roles,sees_money,updated_at`, then replace both local tables in one transaction. Runs on sign-in (awaited, G5), at start (background) and on "Check again". 3d-2b's pull replaces it.
- **G8. Your name reaches the server.** In the live source a `me.name` write first `PATCH`es `profiles?id=eq.<me>` (`display_name` only; allowed by `profiles_self_update`), then writes locally. Offline or refused, the batch fails and the existing "Not saved" path shows. Without this the next team refresh would silently undo the rename. `log.add`, `log.remove`, `notification.read` and `notify.set` stay local until 3d-2b.
- **G9. Roles and "sees money" live in a new table, not on `profiles`.** `public.member_access(profile_id uuid primary key references public.profiles(id) on delete cascade, roles text[] not null default '{}' check (roles <@ array['owner','scout','outreach','deal_lead','delivery']::text[]), sees_money boolean not null default false, updated_at timestamptz not null default now(), updated_by uuid null)`, with the `touch_updated_at` trigger and an `(updated_at, profile_id)` index for 3d-2b's pull. **Why a table:** `profiles_self_update` lets a member update every column of their own row. Columns there would need column-level `revoke update`, which (a) a table-level `grant update` — exactly what `schema.sql` issues on every run — silently overrides, and (b) changes the privileges of a table the old app writes. A trigger guard would also sit on the old app's table. A separate table changes nothing the old app reads or writes. **Who may write:** RLS on, one policy `member_access_read` (`for select to authenticated using (public.is_authorized() or profile_id = (select auth.uid()))`), **no** insert, update or delete policy; grants: `select` to `authenticated`, all four to `service_role`, nothing to `anon` (least privilege; if `schema.sql` is ever re-run its blanket grant would add write privileges, and RLS with no write policy still refuses). Writes go only through `public.set_member_access(p_profile_id uuid, p_roles text[], p_sees_money boolean) returns void`, a `security invoker` wrapper (the one PostgREST exposes) over `private.set_member_access(…)`, `security definer`, `set search_path = ''`, in a new schema `private` that the Data API doesn't expose (the supabase skill's rule for definer functions). It raises `42501` unless the caller is authorized **and** holds `owner` (`private.is_owner()`), `22023` on an unknown role or a missing profile, and `P0001` ("the team needs an owner") if the change would leave no Owner; it stamps `updated_by`. Execute: revoked from `public` and `anon`, granted to `authenticated`; `usage on schema private` to `authenticated` only. **Bootstrap:** no row means no roles and no money. The first Owner row is written once by the lead through the MCP with the owner's go (R1); until step 9 the owner manages the rest with the SQL in `docs/setup.md` (as `postgres` in the SQL editor, which RLS doesn't bind). Access (`profiles.role`: unauthorized, basic, full) is unchanged and still set the old way; `basic` and `full` stay identical in the database.
- **G10. Money: effective rule and where it hides.** A member sees money if they hold `owner` or `sees_money` is true (core `seesMoney(access)`). The **main process strips** prices before the frame crosses: `Deal.price` becomes `number | null` and is `null` for everyone else, so the page never holds a number it must hide. The renderer shows no money when `Frame.seesMoney` is false: the deal line in the peek, the palette and the record page drops its "· $…" part; Settings › Notifications hides the "Money" switch; notifications of kind `money` are filtered out by the source. The database keeps money readable by every authorized member until steps 10–11 (owner, 2026-10-20), so this is a UI promise only; ADR 0011 says so plainly.
- **G11. What replaces `me === "u1"`.** "Mine" means `member.id === frame.me`; "the owner" means `isOwner(member)` (roles include `owner`). `rail.tsx`, `top-bar.tsx` and `settings/sections.tsx` drop every `"u1"`; `avatarColor` takes `isOwner` instead of the id. Owner-only Settings sections (`owner: true`: facts, team, connections), their palette rows and the account menu's "Connections" item are hidden from non-owners. The role label is the member's roles in the fixed order Owner, Scout, Outreach, Deal lead, Delivery joined by " · " (strings in `strings.ts`), or the access label when the list is empty; `TeamMember.title` goes (the example fixtures move to roles and bump `exampleSeedVersion`: u1 Owner; Sara Deal lead · Delivery; Omar Scout · Outreach (the owner's example); Lina Scout).
- **G12. IPC.** New file `packages/ipc/src/auth.ts`, entries in `channels`:
  - `auth:status` `{}` → `{ state: "unconfigured" | "signed-out" | "waiting" | "signed-in", email: string | null }`.
  - `auth:sign-in` `{ email: z.email().max(254), password: z.string().min(1).max(1024) }` → `{ ok: true, state: "waiting" | "signed-in" } | { ok: false, problem: "invalid" | "unconfirmed" | "rate-limited" | "offline" | "no-safe-storage" | "unavailable" }`. The password is used once and never stored, logged or echoed: the schema error text must not contain it (a test), and the handler's errors carry codes only.
  - `auth:recheck` `{}` → the `auth:status` response (the waiting screen's "Check again"; refreshes the profile and team).
  - `auth:sign-out` `{}` → `{}`, then main logs out (best effort, `scope=local`), deletes the session and the live copy (G6), and reloads the window.
  - `frame:load` and `data:write` keep their schemas (plus G10/G11 fields) and use `Account.source()`; with no open source they reject (the page never calls them then).
  No channel carries a token, key, URL or path. Main-to-page events wait for 3d-2b.
- **G13. Team keys: the YouTube key.** Vault secret named `team_youtube_key` (the owner adds it in the dashboard, `docs/setup.md`). `public.team_youtube_key() returns text` (invoker wrapper) over `private.team_youtube_key()` (`security definer`, `set search_path = ''`): raises `42501` unless `public.is_authorized()`, returns `(select decrypted_secret from vault.decrypted_secrets where name = 'team_youtube_key')` or null when unset. Same grants as G9. Main: `main/account/team-keys.ts` `youtubeKey(): Promise<string | null>` calls the RPC **on demand** and caches the value in memory for at most one hour; sign-out and a session end clear it. **Not written to disk**: YouTube calls need the network anyway, and a revoked member loses it at the next fetch. 3e's job supervisor calls it when a run starts and passes it to the pipeline on stdin (architecture's rule). No IPC channel exposes it.
- **G14. Team keys: R2 through the `r2-access` Edge Function.** Deno, no imports beyond relative files, `verify_jwt = true` (kept on, as Supabase advises). Request `POST /functions/v1/r2-access` with the member's `Authorization: Bearer` and the `apikey`, body `{ requests: [{ op: "get" | "head" | "put" | "delete", key } | { op: "list", prefix, continuationToken? }] }` (1 to 50). **Authorization:** the function calls `POST {SUPABASE_URL}/rest/v1/rpc/is_authorized` with the caller's own `Authorization` header and the project's publishable key (from `SUPABASE_PUBLISHABLE_KEYS` → `default`, else `SUPABASE_PUBLISHABLE_KEY`, else `SUPABASE_ANON_KEY`), so PostgREST validates the token and the database decides; not `true` → 403. No service key is used. **Object keys** (the legacy layout, CONTEXT §4 and `legacy/pipeline/gratovo/r2.py`): `channels/<id>.json.zst` (id `[A-Za-z0-9_-]{1,64}`) for get, head, put, delete; `catalog/<worker>/<name>.jsonl.zst` (worker `[a-z0-9-]{1,64}`, name `[A-Za-z0-9._-]{1,100}`) for get and head, and **put only under `catalog/<caller's user id>/`**, so each member writes only their own prefix (new segments; old worker prefixes stay readable); delete never under `catalog/`. `list` takes a prefix `channels/` or `catalog/…` (≤ 200 characters) and signs a ListObjectsV2 GET (`list-type=2`, `prefix`, optional `continuation-token`). Anything else → 400 naming the rule, never echoing more than the op. **Expiry:** 900 s (15 min); the response is `{ expiresAt, urls: [{ op, method, url }] }` with `Cache-Control: no-store`. Secrets `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` (the legacy names, so the owner copies them across); any missing → 503 "R2 isn't set up". Signed host: `https://<bucket>.<account>.r2.cloudflarestorage.com` (virtual-hosted), region `auto`, service `s3`, `X-Amz-Content-Sha256: UNSIGNED-PAYLOAD`. **Code split:** `supabase/functions/_shared/sigv4.ts` (pure presign over WebCrypto `crypto.subtle`, runs in Node 24 and Deno) and `_shared/r2-rules.ts` (request parsing and the key rules) are unit-tested in Vitest; `r2-access/index.ts` is a thin `Deno.serve` handler type-checked against a small ambient `deno.d.ts`. Presigned **list** is SigV4-standard but R2's docs name only GET/HEAD/PUT/DELETE; 3e verifies it against the real bucket and moves listing into the function if R2 refuses it. Real-bucket checks wait for 3e (no session holds R2 keys; CI uses fake values).
- **G15. Migrations (additive only).** `supabase/migrations/20261021090000_member_access.sql` (schema `private`, G9) and `20261021090100_team_keys.sql` (G13). Neither touches an existing table, column, policy, grant or function; each new object has explicit grants (the 2026-10-30 rule); both are re-runnable (`if not exists`, `create or replace`, `drop policy if exists`). No `create extension supabase_vault` (installed on every Supabase project; R1 checks production). The SQL runner's stubs gain a minimal `vault` (a `vault.secrets` table, a `vault.decrypted_secrets` view with `decrypted_secret`, `vault.create_secret(text, text, text)`; owned by `postgres`, nothing granted to `authenticated`), so the real migrations run unedited. `test_30_grants.sql` gains a declared list of read-only tables (`member_access`: `authenticated` holds `select` only). Production applies them through the MCP in R1; if `apply_migration` records a different version than the file name, the files are renamed to the recorded versions before merge so `supabase migration list` matches.
- **G16. Testing without production.** Three layers: (1) **SQL tests** in the existing Docker runner for policies, grants and functions (`set local test.uid`, as today). (2) **Server tests (Linux, local Supabase)**, a new CI job, **recommended now** rather than in 3d-2b: it is the only place the hand-written auth client meets real GoTrue, the Vault function meets real JWT claims, and the Deno function actually runs; 3d-2b's sync tests then reuse it. Supabase CLI **2.119.0** via `supabase/setup-cli` pinned by commit SHA (v3.0.1, `version: 2.119.0`); `supabase start` with Studio, Inbucket/Mailpit, Storage, imgproxy, analytics/vector, Realtime and the pooler turned off in `supabase/config.toml` (Realtime returns in 3d-2b); local keys from `supabase status -o env` into the job's environment (the local stack's keys are throwaway, never written to a file in the repo); R2 values are obviously fake (`r2-test-000`) passed through `[edge_runtime.secrets]` `env(…)`; `supabase/seed.sql` adds a fake Vault value (`yt-test-000`) and is local-only (production is never seeded or pushed). Tests in `supabase/server-tests/*.test.ts`, their own Vitest config, `pnpm test:server`; `pnpm test` doesn't run them. Locally they are optional (Docker Desktop plus `npx supabase@2.119.0`). The CLI is **not** a devDependency (its install downloads a binary on every `pnpm install`, Windows CI included). (3) **Electron tests** against a fake Supabase (`e2e/fake-supabase.ts`, `node:http` on 127.0.0.1, random port) through the G2 seam: the fixture always sets `GRATOVO_SUPABASE_URL`, empty for the example-data tests, so a developer's `.env.local` never points the tests at production.
- **G17. Local schema, migration 2.** `apps/desktop/src/main/db/migrations/0002-member-access.ts`: `member_access(profile_id TEXT PRIMARY KEY, roles TEXT NOT NULL /* JSON array */, sees_money INTEGER NOT NULL, updated_at TEXT NOT NULL) STRICT`. Repository `repositories/member-access.ts` (replace all, list). The example seed writes it from the fixtures.
- **G18. Records.** ADR `docs/decisions/0011-accounts-roles-team-keys.md` (G1–G17, alternatives: supabase-js, columns on `profiles` with column grants, a trigger guard, the key in the secret store, `aws4fetch`, a first-run config entry, waiting for the local stack until 3d-2b). ADR 0003 gains "decided in 0011"; SECURITY.md's team-keys row and config sentence point to it; architecture's Security model item 5 is corrected (roles in `member_access`; money hidden in the UI until steps 10–11; `basic`/`full` identical in the database).

### Questions for the owner (recommendations included; none blocks starting)

- **Q1. Signed out, the app shows only the sign-in screen,** and after sign-in your build shows real but mostly empty data (the team; no creators, brands or deals until 3d-2b's sync). Example data stays only in builds without Supabase settings (dev, tests) and returns for you as prototype mode in 3f. *Recommend yes:* real and example data never mix.
- **Q2. No screen to edit roles or "sees money" in 3d-2a.** You set them once with a short SQL snippet in the Supabase SQL editor (`docs/setup.md`), or ask a session to do it through the MCP with your go; step 9's Settings › Team adds the screen. *Recommend yes:* the database rules are what matters now; the screen belongs with the Team section.
- **Q3. The Owner role always sees money,** whatever its switch says. *Recommend yes* (owner-rules: "full access to everything").
- **Q4. Signing out deletes this computer's copy of the team's data** (and, in 3d-2a, local notifications and log lines). *Recommend yes,* for privacy; 3d-2b keeps unsent changes, as the old app did.
- **Q5. Keep the old "anon" key active** until the old app retires. The new app uses a new publishable key; Supabase plans to retire legacy keys by the end of 2026, which could force step 10's timing. *For awareness;* nothing to decide now unless Supabase announces a date.
- **Q6 (flag, from recon §7.15).** `aws_gateway_credentials` stores AWS secret keys as plain text in Postgres. Out of scope for 3d-2a; *recommend* the owner decides its fate with step 3e (the pipeline).
