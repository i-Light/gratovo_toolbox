# Plan: step 3d-2b, the sync engine (part 1 of 2: pull, outbox, live events)

3d-2b is too big for one pull request, so this plan splits it in two (D1). **3d-2b-1 (this plan):** the sync engine in main over 3d-2a's `Network` and `Session`: local migration 3 (`_outbox`, cursors in `_meta`), keyset pull of `channel_state`, `brands`, `deals` and `activity_log` with tombstones, the resurrection guard and the purge horizon; `profiles`, `member_access` and the new per-person switches read whole each pass (the 3d-2a team refresh folds in here); a FIFO outbox of intent for the four write kinds that reach the server (your name, log lines, undo and redo as new log lines, notification switches) with the old app's refusal rules; drain-before-pull and pending rows never overwritten; main-to-page events (`frame:changed`, `sync:status`) and the persister's "replace without writing" hook; a minimal sync status; sign-out keeping unsent changes; the frame-size, cursor-precision and money-in-notifications fixes; and the one additive Supabase migration (`creator_stage`, `sells`, `status`, `flow_step`, `activity_log.received_at`, `notification_switches`). **3d-2b-2 (next, outlined at the end):** compare-and-set through `apply_channel_edit`, conflicts, the write kinds for a creator's stage, a brand and a deal's step (with the legacy fields), Realtime (`gratovo:live`) and presence (`gratovo:workspace`). Read `.router/CONTEXT.md` first (§1, §3, §5, §9, §10). Bash commands start with `export PATH="$HOME/.local/opt/node-v24.22.0-win-x64:$HOME/.local/bin:$PATH";`. **Never read `.env*` or `*.local.json` files** (`apps/desktop/.env.local`, the legacy `data/.env`), and never read, print or handle a key value. No task touches the production Supabase project: that is the lead's rollout (R1), one step at a time with the owner's go.

Docs checked on 2026-10-20 for this plan: **Supabase changelog 2026** (breaking or relevant: new public tables not exposed to the Data API without explicit grants, enforced 2026-10-30; the `realtime` schema locked against changes since 2026-07-14, while RLS policies on `realtime.messages` still work; Realtime and presence are built in 3d-2b-2 (D23).

## Goal

A signed-in member's local copy fills from the team's Supabase project and stays in step with it: creators, brands, deals, the team with roles, and the activity log, including what the old app writes. Changes the app makes that belong on the server (your name, log lines, undo and redo, your notification switches) are saved on this computer at once and reach the server in order, even after a restart or a day offline; nothing the server refuses is retried forever, and nothing unsent is overwritten by a pull. The open window updates when the data changes, without losing Undo, and the top bar tells the truth about whether changes have synced. The old app keeps working on the same rows, because the one migration only adds.

### Non-goals

Compare-and-set edits through `apply_channel_edit`, conflicts and their notice, and write kinds for creators, brands and deals (3d-2b-2). Realtime broadcast and presence (3d-2b-2; until then a teammate's change shows within the 20 s catch-up). Mirroring the other 15 legacy tables (outreach, templates, campaigns and the rest: their steps 4 to 9). Any new screen beyond the sync state in the top bar, one line on the sign-in screen and a toast (D17). Encrypting `gratovo.db` (D20, Q2). Locking money in the database (steps 10–11). The `search-1`, `first-1`, `mail-1`, `mail-2` gaps.

## Decisions

- **D1. Two pull requests.** 3d-2b-1 (this plan) is everything the pull and the outbox need, end to end, with the four write kinds that exist today. 3d-2b-2 adds compare-and-set, conflicts, the creator, brand and deal write kinds and Realtime with presence. Why this cut: part 1 is useful alone (real data in the app, changes that reach the server), it has no new runtime dependency and no Realtime in CI, and every rule part 2 needs (pending rows never overwritten, the refusal rules, events to the page) is built and tested first. Cost: teammates see each other's changes within 20 s rather than at once until part 2.
- **D2. One engine in main, one pass at a time.** `apps/desktop/src/main/sync/`: a pass is (1) drop outbox rows of any other user, (2) drain the outbox, (3) refresh the whole tables, (4) check the horizon, (5) seed the tombstone cursor on a first pull, (6) keyset-pull `channel_state`, `brands`, `deals`, `activity_log` in that order, (7) pull tombstones. Single flight: a trigger during a pass runs one more pass after it. Triggers: start (after the session is restored), sign-in, a write (1 s after the last one), the 20 s catch-up tick, `sync:now`. Pass budget 2 min; an unfinished pull carries on next pass from its stored cursor. The engine uses the account's one `Rest` (so one single-flight `accessToken()`; a second refresher would end the session on a rotated token, CONTEXT risk 15). It never opens a second database connection.
- **D3. What is pulled in 3d-2b-1.** Keyset: `channel_state` (cursor `updated_at`, key `channel_id`), `brands` and `deals` (`updated_at`, `id`), `activity_log` (`received_at`, `id`, D5). Whole each pass (tiny, and two have no tombstones): `profiles`, `member_access`, `notification_switches` (RLS returns only your row). Tombstones only for `channel_state`, `brands`, `deals` (`table_name=in.(…)`). `sync_control` for the horizon. The other 15 legacy tables stay unpulled until their steps; the old app keeps writing them, and nothing here reads them.
- **D4. Keyset pages and cursor precision.** Query: `select=<columns>&order=<cursor>.asc,<key>.asc&limit=<n>&or=(<cursor>.gt."<c>",and(<cursor>.eq."<c>",<key>.gt."<k>"))` (three-part for tombstones), every value double-quoted (`"` and `\` escaped) and the whole parameter `encodeURIComponent`ed, so a `+00:00` never turns into a space. The cursor is the **last row's raw text** from the server (µs, `+00:00`), stored in `_meta` `sync.cursor.<table>` as JSON `{ at, key }`; it never passes through `Date`. Page 500, halved on a timeout or 5xx down to 25 (`sync.page.<table>`), back up by doubling after 5 good pages; request timeout 45 s. A page whose last cursor equals the stored one stops that table for this pass and logs `pull.stalled` (legacy). Each page is applied in one `BEGIN IMMEDIATE` transaction (a few ms; `node:sqlite` is synchronous) with an `await` on `setImmediate` between pages, so IPC answers between them. Rows are written with `INSERT … ON CONFLICT(<key>) DO UPDATE SET …` over every pulled column, **not** `INSERT OR REPLACE`: that deletes the row first, changes its `rowid` (the frame's order) and would drop local-only columns. Timestamps stay server text in the mirror; ordering and comparisons go through `compareServerTime` (µs) or the local `activity_log.at_ms` (D11).
- **D5. `activity_log` gets a server receive time.** Its `at` is the writer's clock (baseline comment), so a teammate who was offline uploads lines with an `at` older than my cursor and a keyset on `at` never sees them. Additive column `received_at timestamptz not null default now()` and index `(received_at, id)`; the app pulls by it and never sends it. Existing rows all get the migration's time (one value; the `id` tie-break pages them). The old app doesn't select it (its pull names its columns, `mirror_puller.dart` L613) and its inserts get the default. Why not an overlap window on `at`: any window can be outrun by a longer absence.
- **D6. Tombstones, the resurrection guard and the horizon.** **Seed:** on the first pull (no `sync.seeded`), before any data page, the tombstone cursor is set to the newest tombstone (`order=deleted_at.desc,table_name.desc,row_id.desc&limit=1`), or to the server's `-infinity` when there is none; deletions older than the seed are of rows the data pull won't bring, so the first pull reads none of production's ~38k tombstones. **Apply:** `DELETE` the local row only when it has no pending outbox entry and its `updated_at` is older than `deleted_at` (`compareServerTime`), so a row re-created after its deletion survives a tombstone pulled after it. **Horizon:** each pass reads `sync_control.tombstones_purged_before`; if the stored tombstone cursor is older, every cursor resets, `sync.seeded` goes, and the next pull is a full one that marks every key it sees in a `TEMP` table; at its end, local rows of the three tables that weren't seen and have no pending entry are deleted. The outbox is never touched.
- **D7. The outbox of intent.** Local `_outbox(seq INTEGER PRIMARY KEY AUTOINCREMENT, user_id, kind, payload /* JSON */, target_table, target_key, created_at, attempts, last_code)`, plus `_outbox_dropped` (what the server refused: seq, kind, payload, code, dropped_at). Kinds in 3d-2b-1: `profile.name` `{ name }` → `PATCH profiles?id=eq.<me>` `{display_name}`; `activity.add` `{ row }` → `POST activity_log?on_conflict=id` with `Prefer: resolution=ignore-duplicates,return=minimal`, up to 200 consecutive rows in one request; `notify.set` `{ switches }` → `POST notification_switches?on_conflict=profile_id` with `resolution=merge-duplicates`. Rows are enqueued in the **same transaction** as the local write (D11), so a crash can't keep one without the other. Strict FIFO: the head is sent first, and a retryable failure stops the drain ("sending entry 7 after entry 6 failed would apply an edit on a state the server never reached", legacy uploader ~L113). Each row carries the user id; the engine sends only the session user's rows and deletes any other user's at the start of a pass (they can only appear in a file G6 should have wiped). `updated_at` is never sent; the server stamps it.
- **D8. Refusal rules, ported exactly.** From `isFinalUploadRefusal` (uploader L54-68): a PostgREST error with code `42501`, any `22…` or any `23…` → **drop** (move to `_outbox_dropped`, count it, toast once, D17). Schema behind (`PGRST202`, `PGRST204`, `PGRST205`, `42883`, `42703`, `42P01`) → **retry**: a forgotten migration must not lose edits. HTTP 401 after Rest's one refresh, or an `AuthError` → **session**: stop the pass, keep the row (the session manager decides whether it ended). Offline, timeouts, 5xx, 429 and anything else → **retry**. A drop is the only data-loss path, so the app only builds payloads the server accepts (tests) and every drop is visible.
- **D9. Retries and "stuck".** After a pass that failed, the next one waits 30 s, 2 min, 10 min, then 30 min (legacy ladder); a good pass returns to the 20 s tick; `sync:now` runs at once and resets the ladder. The head's `attempts` grows once per pass that fails on it; at 4 (legacy `kOutboxStuckPasses`) the status says `stuck` (D17). Nothing is skipped past a stuck head.
- **D10. Unsent work is never overwritten** (CONTEXT risks 2, 9). Three rules, each tested: (1) drain before pull in the same pass; (2) the puller skips a pulled row whose `(table, key)` has a pending outbox row (the server's newer copy comes back on a later pass, after the entry is sent: its `updated_at` moves past the cursor), and the whole-table refresh writes back a pending `profile.name` and `notify.set` over what it read; (3) the page adopts a new frame only while its persister is idle and its data hasn't changed since it asked (D16). 3d-2b-2's compare-and-set adds "re-fetch the row after a conflict or a drop", which part 1's kinds don't need (the whole tables are re-read every pass).
- **D11. Write intents and the log's shape.** In the live source each `data:write` runs a hook inside the batch's transaction (`onWrite`, Contracts): `me.name` → local write, then `profile.name` with the same cleaned name. `notify.set` → local write, then `notify.set`. `notification.read` → local only (no server twin). `log.add` → a local row in the **server's shape** (`action = 'updated'`, `entity_type = 'app'`, `entity_label = text`, `detail = {"text": …, "app": "toolbox"}`, actor id, the actor's name and role from the local profile, `at` as ISO text) and `activity.add` with the same row; if that id already exists and is hidden by an undo (a redo), a **redo marker** instead. `log.remove` (an undo) → if the line's `activity.add` is still unsent, delete both (it never reached anyone); else keep the line and add an **undo marker**, enqueued as `activity.add`. Markers: a new UUID, `action = 'deleted'` (undo) or `'created'` (redo) (both in the old app's vocabulary, `activity_log_entry.dart`), `entity_type = 'activity_log'`, `entity_id` = the line's id, `entity_label` = its text, `detail = {"undo": true}` or `{"redo": true}`. The server only ever gets inserts (append-only, owner 2026-10-20). The frame hides markers and every line whose newest marker is an undo. Lines from the old app become text through core `logText(row)` (D14), e.g. "Changed stage of @handle: shortlisted → contacted". Lines written by 3d-1/3d-2a (local shape: `entity_type = 'app'`, no `detail`) read their `action` as text and stay local. Local migration 3 adds `activity_log.at_ms` (backfilled), `received_at`, and indexes on `(at_ms DESC, id DESC)` and `(entity_type, entity_id)`; `newestLog` orders by `at_ms`, because ISO text with `Z` and with `+00:00` don't sort together.
- **D12. Read rules for the app's own columns.** `creatorStageFrom` and `dealStepFrom` use `creator_stage`/`flow_step` only when the legacy fields still say what the app wrote (`legacyCreatorFields(stage)` equals the row's `vetting_status`/`pipeline_stage`; `legacyDealStage(step)` equals `stage`); otherwise the old app changed them since and the legacy fields win (derived as today). No server trigger on the old app's tables. `brands.sells`/`status` have no legacy twin: null reads as `""` (sells) and `"found"` (status).
- **D13. The frame stays inside the IPC limits** (CONTEXT risk 1). `listMax` stays 5000. `listCreators` returns at most 5000: every creator a deal names first, then creators past `new` (`creator_stage` set or the legacy fields not `newlyFound`/`new`), then the most recently updated; one SQL query with `LIMIT`, `primaryEmail` only for those rows. Notifications are read newest first with `LIMIT 5000`; brands and deals are tiny today and keep their cap (a test proves an over-cap table is cut, not a failed `frame:load`). Measured in the contract suite: 20,000 `channel_state` rows give a frame that passes `frameSchema`, holds every deal's creator, and serialises under 2 MB. Step 5 replaces the palette's creator list with a search query (ADR 0010) and can lift the cap.
- **D14. Money can't leak through notifications or the log** (closes ADR 0011's consequence). Notifications: local column `notifications.money` (set by whoever creates one with an amount) plus a backstop, core `mentionsMoney(text)` (a currency sign or code next to a number); for a member without money, a notification of kind `money`, flagged `money`, or whose text or sub mentions money is dropped. Log lines: for a member without money, a line whose `field` is in core `moneyFields` (`brand_price`, `influencer_payout`, `budget`) or whose text mentions money is dropped from the frame. Dropping, not editing: a hidden line can't half-show an amount.
- **D15. Main-to-page events.** One Electron channel `gratovo:event` carrying `(name, payload)`. Names and payload schemas in `packages/ipc/src/events.ts`: `frame:changed` `{ parts }` (which parts of the frame changed: `team`, `me`, `creators`, `brands`, `deals`, `log`, `notify`) and `sync:status` (the status, D17). Main validates every payload against its schema before sending, and sends only to the app's own windows (the page URL check `isTrustedSender` uses); a bad payload is logged by name and dropped. The preload adds `on(name, listener) → unsubscribe` to the bridge: it registers one `ipcRenderer.on` per call, passes the listener the payload only (never the Electron event), ignores names not in the list, and imports only types and constants (`bridge.ts`), so the sandboxed preload still bundles no zod. During a long pull `frame:changed` goes out at most once per 2 s and at the end of each table.
- **D16. The page adopts server data without writing it and without losing Undo.** `renderer/lib/live.ts` listens for `frame:changed`, waits for `persistenceIdle()`, notes the store's data, calls `frame:load`, and applies the answer only if the data is still the one it noted and the persister is still idle; otherwise it waits for the next idle and asks again (at most once a second). Apply = `adoptServerData(next)` in `persist.ts`: sets an `adopting` flag, runs `store.bg(draft => mergeServerData(draft, next))`, and the persister takes the result as its baseline with nothing written. `mergeServerData` replaces `team`, `creators`, `brands`, `deals`, `seesMoney` (the page can't change them yet), inserts log lines it hasn't got and removes teammates' lines that are gone (newest first, 50 kept), and takes `myName` and `notify` only when `parts` names `me`/`notify` and the persister has nothing pending. `bg` applies the same recipe to every undo and redo step, so undoing an older change never removes a teammate's line or writes a `log.remove` for it. A changed account or access still reloads the window (3d-2a).
- **D17. The sync state is visible, minimally.** IPC `sync:status` (`{}` → status) and `sync:now` (`{}` → status after one pass) and the `sync:status` event. Status `{ state: "off" | "syncing" | "synced" | "offline" | "stuck", pending, refused, lastSyncedAt }`; `off` with no live source (unconfigured, signed out, waiting), where `pending` counts changes kept from a signed-out session (D18). UI, three things only: (1) the top bar's save chip keeps "Saving…"/"Saved"/"Not saved" for the local write, and shows **"Not synced"** when changes wait and the state is `offline` or `stuck`; its tip says what is true ("Saved on this computer and synced 2 min ago", "Saved on this computer. 3 changes will sync when you're back online.", "Saved on this computer. A change keeps failing to sync; it will keep trying."). (2) A toast when `refused` grows: "The server refused a change" / "It stays on this computer only." (3) One quiet line on the sign-in screen when a signed-out copy holds unsent changes: "3 changes from your last session are waiting on this computer. Sign in to send them." All words in `renderer/strings.ts`.
- **D18. Sign-out keeps unsent changes** (owner, 2026-10-20). The page waits for its persister as today, then calls `sync:now` once; then `auth:sign-out`. Main gives the drain up to 5 s more; if the outbox is empty, it deletes `gratovo.db` as in 3d-2a. Otherwise it keeps the file with **only** `_outbox` and `_meta.account.user_id`: one transaction deletes every row of the mirror and local tables, `_outbox_dropped` and every other `_meta` key, then `VACUUM` (so freed pages don't keep the data) and close. At start, a copy without a session is deleted unless it holds outbox rows. Signing back in as the same account keeps the file (G6 matches the user), pulls from scratch and sends the rows first. A server-ended session keeps unsent rows the same way. **Signing in as someone else deletes them** (G6 still holds; logged with the count; Q3). Demotion to waiting deletes the copy (the server would refuse the rows with 42501 anyway).
- **D19. The team refresh and the name PATCH fold into the engine.** `account/team-refresh.ts` becomes `sync/whole-tables.ts` (the same columns and replace-in-one-transaction, plus `notification_switches` → local `notify`, plus D10's pending rule); `account/live-writes.ts` goes (the name is an outbox row). Sign-in still waits for the whole tables (not the keyset pull) before answering, so the first frame shows the team. **Changed behaviour:** offline, a rename now saves locally and shows "Saved" with the waiting tip, instead of "Not saved"; the 3d-2a e2e expectations change with it.
- **D20. `gratovo.db` stays unencrypted (pending Q2).** With real data it holds ~15.6k creators' contacts. `node:sqlite` has no encryption, SQLCipher would bring back the native module ADR 0010 avoided, and encrypting columns would break the searches steps 4–9 run on them. The file lives in the Windows account's own profile, is deleted on sign-out (D18), and holds the same as the old app's unencrypted file. `docs/setup.md` advises BitLocker on every team computer. Revisit if a computer is shared.
- **D21. The Supabase migration (additive only).** `supabase/migrations/20261022090000_sync_columns.sql`: `channel_state.creator_stage text` (check: null or one of the 11 `creatorStages`), `brands.sells text` (≤ 500 characters), `brands.status text` (≤ 40), `deals.flow_step smallint` (0 to 9, `DEAL_FLOW`), `activity_log.received_at` and its index (D5), and `public.notification_switches(profile_id uuid primary key references public.profiles(id) on delete cascade, switches jsonb not null default '{}' check (jsonb_typeof(switches) = 'object'), updated_at timestamptz not null default now())` with `trg_notification_switches_touch` (`touch_updated_at`), RLS on, policies `notification_switches_read` (select), `_insert`, `_update`, each `to authenticated` with `profile_id = (select auth.uid()) and (select public.is_authorized())`, no delete policy; grants: `revoke all … from anon`, `select, insert, update, delete` to `authenticated` (test_30's rule; RLS has no delete policy), all to `service_role`. Named constraints dropped and re-added, so it re-runs cleanly; the runner's second pass (after a `schema.sql` re-run) must leave the same privileges. Nothing else changes: no existing column, policy, grant, trigger or function, and the old app's pull names its columns, so it never sees the new ones; its row upserts carry only its columns, so they leave the new ones as they are. Production applies it in R1. Brief locks: the checks scan ~15.6k `channel_state` rows (well under a second); `received_at`'s default is a constant default (no rewrite).
- **D22. Tests without production.** SQL tests (Docker) for the migration. Server tests (the existing job) run the app's own puller, uploader and whole-tables modules on a temporary `node:sqlite` file against the local stack; Realtime stays off in `config.toml` and CI until 3d-2b-2. Electron tests extend `e2e/fake-supabase.ts` with the sync tables (it implements the exact `or=(…)` shape the app sends, with fixed-width µs timestamps so text order is time order) and drive passes with `window.gratovo.invoke("sync:now")`, so no timer seam is added.
- **D23. No new runtime dependency in 3d-2b-1; Realtime in 3d-2b-2 uses `@supabase/realtime-js` 2.117.2.** It fits behind the allowlist: `transport` is a WebSocket class exported from `net/network.ts` that runs `checkWebSocketUrl` first, `fetch` is `network.request`, `params.apikey` the publishable key, `accessToken` the session's single-flight token. Hand-rolling Phoenix join, heartbeat, presence diffs and reconnect would be ~300 lines of protocol we'd own for no gain. Recorded here so part 2 doesn't reopen it.
- **D24. Records.** ADR `docs/decisions/0012-sync-engine.md` (D1–D23; alternatives: `INSERT OR REPLACE`, an `at` cursor with an overlap, seeding tombstones to "now" from the client clock, a server trigger to clear `creator_stage`, raising `listMax`, file encryption with SQLCipher, a sign-out that refuses with pending changes, hand-rolled Phoenix). ADR 0010's open items (IPC limits, encryption) and ADR 0011's consequences (team refresh, name PATCH, unsent changes on sign-out, money in notifications) point to it.

### Questions for the owner (recommendations included; none blocks starting)
