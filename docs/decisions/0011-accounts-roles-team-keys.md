# 0011. Accounts, roles and team keys

- **Date:** 2026-10-20
- **Status:** accepted for step 3d-2a (sign-in, roles, the network allowlist, team keys). Step 3d-2b (the sync) builds on it. Answers the questions [0010](0010-data-layer.md) left for 3d-2 about roles and production's Postgres major, and settles the team keys [0003](0003-secrets.md) left open.

## Context

After 3d-1 the app read and wrote a local database but had no account: it always opened the example data, and "the owner" was the hard-coded member `u1`. The owner split 3d-2 in two (2026-10-20). 3d-2a lets a team member sign in with email and password, as in the old app, and lands them on their own account with the team, their agency roles and no money unless they may see it. It also brings the team keys: the old app shipped them in a tracked `data/.env`. The old app keeps running against the same Supabase project until step 10, so every server change only adds.

The owner's answers (2026-10-20): agency roles are a list per person, apart from access, with "sees money" as its own switch; money is hidden in the new app now and locked in the database when the old app retires; the YouTube key goes in Vault and R2 access is short-lived signed links, both built now; production changes go through the Supabase MCP with the owner's go before each one; the owner enters key values in Supabase themselves.

## Decision

1. **Plain `fetch` in the main process, no `@supabase/supabase-js`.** 3d-2a makes seven kinds of call: password sign-in, refresh, logout, a PostgREST select, an RPC, a PATCH and one Function call. Owning them means the session lives exactly where we put it, every request goes through the allowlist, and tests fake one function. The cost is the refresh logic and the error mapping, both small, and the server tests run them against real Supabase Auth. No new runtime dependency.
2. **The app's Supabase settings are the project URL and the publishable key, set at build time** (`MAIN_VITE_SUPABASE_URL`, `MAIN_VITE_SUPABASE_PUBLISHABLE_KEY`, from the environment or `apps/desktop/.env.local`). `main/supabase/config.ts` checks them at start: the URL must be `https://<20 letters or digits>.supabase.co`, and the key must start with `sb_publishable_`. It refuses a secret key or anything shaped like a JWT (a legacy `anon` or `service_role` key), and logs the problem's name, never the value. No settings means **unconfigured**: example data and no sign-in, as in dev and the tests. An unpackaged app can be pointed at a test server on `http://127.0.0.1` through `GRATOVO_SUPABASE_*`; a packaged one ignores the environment.
3. **One door to the network.** `main/net/network.ts` sends a request only to an allowed origin (the project's, or the test server), over https, with no user name or password in the URL, with redirects refused and a timeout. An ESLint rule forbids `fetch`, `WebSocket`, `node:http` and the like anywhere else in main. The page stays on `connect-src 'self'`, and `blockForeignRequests` cancels any request from the page's session that isn't the app itself.
4. **The session is stored as the refresh token only,** in the secret store (`safeStorage`, the Windows account's key), as `supabase.session`. The access token stays in memory, so a start costs one refresh. Refreshes are single flight, 60 s before expiry, backing off 30 s, 2 min and 10 min after a network failure. The session ends only on Auth's own codes (`refresh_token_not_found`, `refresh_token_already_used`, `session_not_found`, `session_expired`, `user_banned`, or a 400/401 without a code). Network errors, 5xx and 429 keep it. Errors and logs carry a code and a status, never a body, token, password or email. No IPC channel returns a token, password or key. Checked on a local stack: a refresh token reused outside the reuse window is refused with `refresh_token_already_used` and the session lives on, so the app signs in again rather than assuming the server ended it.
5. **Four states at start:** unconfigured, signed out (the sign-in screen), waiting (signed in, but access is still `unauthorized`: "The owner hasn't let you in yet."), signed in (the live database, `me` is the account). With a stored session the app opens the local copy at once and checks the session and the team in the background. If the check finds the session ended or the access dropped, main reloads the window and the page starts over. A first sign-in waits for the team to load, so the first frame shows it.
6. **The local copy belongs to one account.** Signing out, signing in as someone else, being demoted to `unauthorized`, or the server ending the session deletes `gratovo.db` and the session. A waiting member keeps no local copy, and a copy found without a session at start is deleted. In 3d-2a nothing unsent is lost this way except local notifications and log lines; 3d-2b keeps unsent changes.
7. **The team refresh is a stopgap** until 3d-2b's pull: on sign-in, at start and on "Check again", it reads `profiles` and `member_access` and replaces both local tables in one transaction. **Your name reaches the server:** a rename PATCHes your own `profiles.display_name` first, then writes locally; offline, it fails and the bar shows "Not saved".
8. **Roles and "sees money" live in a new table, `public.member_access`,** not on `profiles`. `profiles_self_update` lets a member update every column of their own row, so a roles column there would be self-editable, and column-level revokes would be undone by `schema.sql`'s blanket grant on every run. The new table has row-level security with one read policy (an authorized member reads every row; anyone else only their own) and no write policy. Writes go only through `public.set_member_access`, a `security invoker` wrapper over `private.set_member_access` (`security definer`, empty `search_path`, in a schema the Data API doesn't expose). It refuses anyone but an authorized Owner (`42501`), an unknown role or missing member (`22023`), and a change that would leave no Owner who can still sign in (`P0001`). It takes an advisory lock, so two owners can't remove each other at the same moment. Access itself (`profiles.role`: unauthorized, basic, full) is unchanged and still set the old way.
9. **Who sees money:** an Owner always does; anyone else only with the switch on. The main process sets every deal price to `null` before the frame crosses to the page and drops money notifications, so the page never holds a number it must hide. **This is a promise of the new app only:** the database still lets every authorized member read prices until steps 10 and 11, because the old app reads them for everyone.
10. **"The owner" means a member whose roles include Owner,** not the member `u1`. Owner-only settings sections, their palette rows and the Connections menu item are hidden from everyone else.
11. **The YouTube key is in Supabase Vault** under `team_youtube_key`, read through `public.team_youtube_key()` (invoker wrapper) over a `private` definer function that refuses anyone not authorized. Main fetches it on demand and keeps it in memory for at most an hour; it is never written to disk and no IPC channel exposes it. Its first user is the pipeline (3e), which gets it on stdin.
12. **R2 access is short-lived signed links from the `r2-access` Edge Function** (`verify_jwt` on). The function asks the database, with the caller's own token, whether they are authorized; it uses no service key. Keys must follow the old layout (`channels/<id>.json.zst`; `catalog/<worker>/<name>.jsonl.zst`), a member writes only under their own catalog folder, and catalog objects can't be deleted. Links last 15 minutes and carry `no-store`. The SigV4 signer (about 100 lines over WebCrypto) matches AWS's published example. The four R2 values are Edge Function secrets with the old names.
13. **Migrations only add.** `20261021090000_member_access.sql` and `20261021090100_team_keys.sql` touch no existing table, column, policy, grant or function, give each new object its own grants, and can be run again.
14. **Three layers of tests without production:** SQL tests in Docker (policies, grants, functions, with a minimal stand-in for Vault); a new CI job, **Server tests (Linux, local Supabase)**, with Supabase CLI 2.119.0, where the app's own auth client meets real Supabase Auth, the Vault function meets real tokens and the Deno function actually runs (it tests the server, not the app, so the Windows-only rule holds); and Electron tests against a fake Supabase on `127.0.0.1`.
15. **The rollout to production** (2026-10-20, through the MCP, the owner's go per step): a migration history table was created with the baseline marked applied (its SQL never run); each migration was applied with its file's exact SQL and its own version, so the history matches the file names; the owner's account was made Owner with money; `r2-access` was deployed. Checked afterwards: every new object is owned by `postgres`; `anon` can run none of the new functions and can't read the new table; members can't write it directly; the Owner gets the Vault key and a stranger is refused; a call to the function without a token gets 401; `private` isn't an exposed schema; the old app still signs in, loads and saves.

## Alternatives considered

- **`@supabase/supabase-js`:** complete, but it brings its own storage, URL session detection and timers, and its requests would bypass the network module unless wrapped. Seven calls don't need it. 3d-2b decides on Realtime separately.
- **Roles as columns on `profiles` with column grants, or a trigger guard:** both change a table the old app writes, and `schema.sql`'s blanket grant silently undoes column revokes.
- **The YouTube key in each machine's secret store:** every member would have to enter it, and a removed member would keep it.
- **`aws4fetch` for signing:** inactive since 2024 and would need an import map in Deno.
- **A first-run screen for the URL and key:** every member would type them. A committed constant breaks the secrets policy.
- **Keeping example data when signed out:** real and example data must never mix. Example data returns for the owner as prototype mode (3f, ADR 0004).
- **Waiting until 3d-2b for a local Supabase in CI:** the hand-written auth client, the Vault function and the Deno function would meet real Supabase for the first time in production.

## Consequences

- Until step 9's Settings › Team, the owner sets roles and "sees money" with the SQL in [docs/setup.md](../setup.md), or asks a session to do it through the MCP.
- If anyone re-runs the old `schema.sql`, it revokes execute on the new wrappers: re-apply the two migrations right after.
- Not yet checked on production: an `r2-access` call with a real member's token, and whether R2 accepts a presigned list. Nothing calls the function before 3e, which checks both against the real bucket.
- Money is hidden by notification kind only: an amount written into another kind of notification would show. 3d-2b's sync, which brings real notifications, closes this.
- A packaged build with bad settings falls back to example data. Fix before the first release build (3h), which must refuse to build without the two values.
- Supabase plans to retire legacy `anon` keys by the end of 2026. The old app uses one, which may force step 10's timing.
- 3d-2b replaces the team refresh and the name PATCH with the sync engine, keeps unsent changes on sign-out, and decides whether `gratovo.db` is encrypted when contact data arrives.
