# 0010. How the local data layer is built

- **Date:** 2026-10-20
- **Status:** accepted for step 3d-1 (the local data layer). Step 3d-2 (sign-in, sync, the team-keys function) adds to it.

## Context

Until step 3d the app showed a typed example constant, and nothing it changed survived a restart. The [architecture](../architecture.md) asks for local-first data: a SQLite database in the main process that the screens read from and write to, kept in step with Supabase by a sync engine. The owner split step 3d in two (2026-10-20). 3d-1 builds everything that works without a network: the database, one interface over it, the app reading and writing through it, and the Supabase schema as a tested baseline. 3d-2 brings sign-in and the sync. Production Supabase already runs the legacy `schema.sql` (A3, owner 2026-10-20). Keys are not rotated for now and are entered at run time only, so nothing in 3d-1 needs one.

## Decision

1. **The contract lives in core.** The domain types, the `DataSource` interface, the five write kinds, the legacy mapping and the example fixtures are in `packages/core/src/data/`, exported as `@gratovo/core/data` (pure, no I/O, so the main process doesn't pull in immer). `packages/ipc` holds the zod schemas, each typed `z.ZodType<CoreType>`, so a schema and its type can't drift apart.
2. **One read, one write.** `frame()` returns everything the frame, palette, peek and record page show; `write(writes)` applies a batch in order in one transaction, all or none. Both return promises although the driver is synchronous, so the database can later move to a utility process without touching callers. The write kinds are exactly the changes the app makes today: a notification read or unread, the notification switches, your name, a log line added or removed.
3. **Driver: `node:sqlite`** (`DatabaseSync`), built into Electron 44.9.0's Node 24.22.0 with SQLite 3.53.4. No native module to rebuild. Checked inside Electron: WAL works, and no ExperimentalWarning is printed. Pragmas at open: WAL, `busy_timeout=5000`, `synchronous=NORMAL`, `foreign_keys=ON`.
4. **Local schema, migration 1.** `STRICT` tables. The mirror tables (`profiles`, `channel_state`, `brands`, `deals`, `activity_log`) carry every remote column the old app's sync used, so 3d-2's pull needs no migration for them. No foreign keys on mirror tables: the server owns integrity, and pages arrive in any order. App columns with no Supabase column yet (`channel_state.creator_stage`, `brands.sells`, `brands.status`, `deals.flow_step`) are nullable; whether Supabase gains them is a 3d-2 question. Local-only tables: `channels` (the scraped name, which lives in R2 until 3e), `notifications`, `local_settings`, `_meta`. No outbox or sync cursor tables yet: nothing in 3d-1 reaches a server, and an unused table is untested.
5. **Migrations run forward only,** versioned by `PRAGMA user_version`. Each is a TypeScript module holding SQL, so the bundler includes it. Each runs in its own transaction that also sets the version; a failure rolls back. A database newer than the app is refused, never downgraded.
6. **Mapping to the old app's fields.** Pure functions in core read the old app's values (`vetting_status`, `pipeline_stage`, a deal's `stage`) when the app's own column is empty, and write both, so the old app keeps working on the same rows. Every branch is tested.
7. **Two sources, one implementation.** `createSqliteSource` serves both. The **example** source is `example.db` in the user data folder, seeded from the AI-niche fixtures through the same repositories when its seed version is missing or older; it persists, so changes survive a restart like real data. The **live** source is `gratovo.db`, empty until 3d-2's sync fills it; it is built and passes the same contract tests, but the app doesn't open it in 3d-1. One shared test suite (`describeDataSourceContract`) runs against both.
8. **The app always opens the example source in 3d-1.** There is no account yet, so live has nothing to show. No environment switch, so there is nothing to leave a trace (ADR 0004). 3d-2 picks the source from the session; prototype mode (3f) switches at run time.
9. **Two channels,** `frame:load` and `data:write` (1 to 100 writes). No path, URL or secret crosses. The schemas bound everything: ids 1 to 100 characters, text 500, names 80, the log 50 lines, lists 5000. A notification's route is plain strings, which the renderer checks against its routes (unknown goes to Today).
10. **Start-up waits for the data.** The main process opens the database before the window, so `frame:load` answers in milliseconds and the dark window shows nothing meanwhile; there is no loading state. If the load fails, the page says "The app couldn't load its data. Close it and open it again." A database that won't open reaches the existing start-up error dialog.
11. **A persister turns data changes into writes.** After every store change it compares the data with the data it last saw, by reference, and turns the difference into writes. Undo and redo swap in the earlier data, so they write their inverse with no extra code; a background change is saved like any other. A change the write kinds can't express is logged as an error and not written. Batches go out in order, one at a time. A change producing more than 100 writes is sent as several batches of 100, each its own transaction (no effect at today's sizes; 3d-2 revisits with real data). A failed batch shows a toast ("That change wasn't saved. It will be gone after a restart.") and isn't retried. A store replaced from the database becomes the new baseline with nothing written, which is the hook 3d-2's sync will use.
12. **"Saved" tells the truth.** The top bar stays on "Saving…" until every write has reached the database, and for at least the 700 ms it showed before. Reading one notification and setting your name write data now, so they show "Saving…" too. If a write fails, the bar shows "Not saved" until the next save succeeds.
13. **Your name is on the account,** in `profiles.display_name` of the signed-in member, as ADR 0009 decision 22 said it would be. The `name` device preference is gone, and a name saved there earlier is ignored. Setting it is still a background change, not undoable.
14. **New ids are UUIDs.** Log lines were `l1`, `l2`…, which would collide after a restart.
15. **The Supabase schema is a baseline migration:** `supabase/migrations/20261020120000_baseline.sql` is `legacy/backend/schema.sql` byte for byte, because that is what production runs; the SQL test runner checks the copy still matches while `legacy/` exists. Production never ran it through the CLI, so 3d-2 marks it applied there (`supabase migration repair`) and never pushes it. From 2026-10-30, every new table in a later migration needs its own `grant` lines.
16. **SQL tests run in Docker,** in a throwaway `postgres:17.11` container pinned by digest (Supabase's current major; legacy used 16): the stubs, the baseline, the baseline a second time (it must re-run cleanly), the later migrations in name order (so the baseline's blanket grants can't hide a missing grant), then the tests, including a new one that checks row-level security and grants on every public table. The runner is a Node script with no dependencies (`pnpm test:sql`). CI runs it in a Linux job, **SQL tests (Linux, Docker)**: it tests the database, not the app, so the Windows-only rule holds. The old pass 2 (upgrading an old schema) is dropped with `migrate_v2.sql`.

## Alternatives considered

- **better-sqlite3:** fast and mature, but a native module that must be rebuilt for each Electron version. `node:sqlite` ships inside Electron.
- **Writes from immer patches:** ADR 0009 left this open. Patches describe paths inside the store's objects, not rows; turning them into rows would tie the database to the store's shape. Diffing the data by reference gives the same writes, also covers undo and redo, and fails loudly on a change it can't express.
- **An in-memory example source:** simpler, but nothing would survive a restart, so the save path would go untested until 3d-2. A seeded file makes the example data behave like real data.

## Consequences

- A new kind of change needs a write kind, its schema, a repository function and a persister rule; until then the persister logs it as a console error. The data e2e tests watch the console from the moment the window opens and fail on any error; other specs don't.
- Screens that arrive later (steps 4 to 9) add their own reads beside `frame()`, and step 5 replaces the palette's record lists with a search query.
- The local file is not encrypted. 3d-2 revisits this when real contact data arrives.
- A live frame larger than the IPC limits (over 5000 creators, a profile name over 80 characters) would fail `frame:load`. 3d-2 revisits the limits when the sync brings real data.
- Questions for 3d-2, none blocking 3d-1: agency roles have no column; the app's creator stages, brand fields and deal steps have no Supabase columns; `activity_log` is append-only on the server while undo removes a line; notification switches are per device; production's Postgres major is unconfirmed.
