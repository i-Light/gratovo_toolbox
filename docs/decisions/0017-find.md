# 0017. Find

- **Date:** 2026-10-25
- **Status:** accepted for step 5 (Find: search, triage, gallery, contacts; Toolbox › Archive, Never contact, Activity log). It records the plan's decisions (D1 to D46 of the step's `.router/PLAN.md`, removed when the step ended and kept in the git history before the 5e merge; 5e's own D47 is item 37 and D48 is this record's layout) as built, over the pull requests #20 to #24 and 5e. Where the build differs from the plan, the build is written here and the difference is said. It amends ADR 0013 §6 (`pipeline.db` is now at schema version 4, not 1) and uses what ADR 0012 (the sync's outbox) and ADR 0016 (`archiveDays`, the live gate) left ready. ADR 0013, 0014, 0015 and 0016 otherwise stand.

## Context

Step 5 takes the owner from keywords to shortlisted creators with confirmed addresses, on real pipeline runs, without leaving Find. Toolbox comes with it: Archive, Never contact and the Activity log.

It was built in six pull requests: 5a (the catalog and Review new), 5b (the gallery and the creator record), 5c (contacts and keyword ideas), 5d (Toolbox), 5d-2 (the archive keeps its data, asked for by the owner after 5d), and 5e (the flow suite and this record).

Three things shaped it. The frame keeps 5,000 creators (ADR 0012), but a pipeline can hold far more channels. Python owns `pipeline.db`, and the page has no network. And YouTube gives no audience split and no engagement figure, so the fit score has to say what it does not know.

## Decision

### The catalog and its queries

1. **The catalog is a read model in main.** `main/find/catalog.ts` joins `pipeline.db` (read-only, `node:sqlite`) with the open data source's `channel_state`. It holds every pipeline channel, plus every `channel_state` row past stage `new`, even without local numbers (`hasNumbers: false`). A row at `new` with no pipeline channel is left out: it has nothing to show until R2 sharing (step T). It is built in memory and rebuilt when `pipeline.db` changes (a store-lane job's keyword or end line) or creator rows change. Rebuilds are coalesced to one every 500 ms, each bumps `version` and emits `find:catalog`.
   *Why:* one place joins the two databases, and the page never reads either.
2. **Queries run in main, the page asks for pages.** `find:query` takes a filter, a sort and a page (at most 120 items) and returns the items, the total and the facet counts. `find:item` returns one creator in detail (up to 15 videos, the description, notes). The filter, sort, fit and facet logic is pure, in `packages/core/src/find/` (`fit.ts`, `filter.ts`), so it is tested once and main only feeds it rows. The page lays its own stage, email and confirmed state over the items it shows, so a key press shows at once; counts catch up on the next `find:catalog`.
   *Why:* a 3,000-channel owner must not send the catalog across the bridge. A timing test builds 3,000 channels with 15 videos each and 16,000 states.
3. **Run history.** `find:runs` returns the newest 50 `search` runs with found, kept and gold counts. A catalog row's `run` is the run whose window holds the channel's first `discovered_at`. "Review results" on the newest run opens Review new. On an older run it opens the gallery with the run in the filter (`runs: [id]`, stages empty). A paused search is recorded `stopped` and shows as a pause. The plan first kept this in a module store in the triage screen; the build put it in the filter itself.
4. **Uploads that were never read are not zero.** `CatalogItem.uploadsRead` is false when a channel has no uploads read. Find then says "Not read yet" (the last known figure under it), never 0 views. Such channels sort last on median and latest, score 0 on median and posting, and are never gold. After three failed reads the card says "Couldn't read" (`readFailed`). A creator with no pipeline row says "No numbers yet" (card) or "–" (table).

### Acting on creators, and the write path

5. **Acting on a creator the frame doesn't hold.** Before an action touches a catalog item that isn't in `data.creators`, the page adds it with `adoptServerData` (current data and every undo step, nothing written). Then `act` changes it as usual, so Undo and the persister work unchanged. The persister writes nothing for an added creator.
6. **A stage write creates the row.** `creator.stage` carries `handle` and `name`. With no `channel_state` row, main inserts one and the `channels` name, then queues the edit with base `null`. The server's `apply_channel_edit` already creates a row for a channel it has never seen. The persister writes records before log lines.
7. **Reject sets the server's tag; the reason travels with the log.** The four reasons are `ai` "Not about AI tools", `views` "Too few views", `posting` "Not posting enough" and `audience` "Audience outside US, UK, CA or AU". A move to `rejected` adds the tag `inactive` for `posting`, else `irrelevant` (the server trigger then sets `archive_due_at`), and sets the local due date to now plus 7 days. A move away removes the tags `irrelevant`, `inactive` and `haramStuff` and clears the date. A log entry gains `ref`, `action` and `detail`; the server row gets `entity_type 'channel'`, `entity_id` and `detail {reason}`. A creator's `rejectReason` and `rejectedAt` come from its newest visible `creator.reject` or `creator.never` line. A keep-mine answer to a tags conflict restores the tags.
8. **Never contact.** Stage `never`, with the reason the person wrote as `detail` of the `creator.never` line (`neverReason`, up to 500 characters; null for any other stage). Never-contact creators are hidden from Review new and the gallery's default view. Searches skip them: the search job takes `skip: channelId[]` (at most 20,000), which `partition_discovered` treats as known. "Allow again" sets stage `new`.
   *Why:* the stage is the one fact step 6's send gate reads.
9. **The reject toast** names the reason and says: "Bring it back from Toolbox › Archive before it is archived for good."

### Fit, gold, and what YouTube can't give

10. **Fit has five parts**, ported from the prototype: median views 30, posting 15, audience 25, engagement 15, sponsored before 15. YouTube gives no audience split and no engagement figure. So the audience part scores the channel's own country (full points for US, GB, CA or AU) and its note says so; engagement uses `manual_engagement_rate` when set, else 0 with "not known yet". The facet is "Channel country", not "Top 3 countries". Gold is median ≥ 40,000, median ≥ 40% of subscribers, and 3 to 20 uploads in 30 days. A hidden subscriber count is unknown: not gold, skipped by the subscriber facet.
    *Why:* a score that pretends to know the audience would be wrong in the way the owner pays for.
11. **"Emailed before"** shows when the legacy `pipeline_stage` is past `new`, or the stage is `emailed` or later, with who and when from the newest activity line when there is one. The full mail history arrives in step 6.

### Pictures through main

12. **The page has no network, so main fetches pictures.** Items carry keys, `v:<videoId>` and `c:<channelId>`, and the page shows `app://gratovo/img/<key>`. Main builds the address itself, never from page input: `https://i.ytimg.com/vi/<id>/mqdefault.jpg` (id checked), or a channel's stored picture only on `yt3.ggpht.com` or `yt3.googleusercontent.com`. It fetches through its own network instance (these hosts, https, no redirects, at most 2 MB, image types only, at most 6 at once) and caches files under `<userData>/image-cache/`, named by the key in hex (Windows ignores case), pruned oldest first past 4,000 files. Example data never fetches: it answers 404 and the page draws initials. The packaged CSP is unchanged (dev adds `app://gratovo` to `img-src`).

### Review new

13. **Review new** shows creators at `new`, gold mines first, then fit: one channel with its last three videos, numbers, sponsors, fit chip and the "emailed before" guard. Keys: S shortlists; R opens the reason row, then 1 to 4; 1 to 4 reject at once; ← → or J K step; O opens the record; Ctrl+Z undoes, everywhere. Keys follow the "letters" switch and never fire while typing. The Find tabs follow the ARIA pattern (← → move between tabs while one has focus), but a mouse click on a tab hands focus to the panel, so the arrows then step through channels (the owner's choice after 5e). (In Toolbox, J and K step through the tools and do nothing while a peek is open.) The next channel shows at once and the tally counts up. The old "Kept" strip was removed.

### The gallery, views, the record and notes

14. **Paging.** The gallery loads 120 at a time and the next page when the last card scrolls into view. "Select all" selects what is loaded and says how many; a bulk action never touches channels not loaded. Shift-click selects a range, Ctrl-click toggles, Ctrl A selects the loaded ones, Esc clears. Cards use `content-visibility`.
15. **Filters, display and saved views.** The filter is `FindFilter` (stages, signals, countries, median and uploads bounds, runs, text), the shape step 9's Insights drill-down will write. The last filter, sort, view (cards or table), card size and the show toggles are device prefs. Saved views live in `local_settings` under `find.views` (at most 20, name up to 60) through `find:views` and `find:views-set`. No "Who has it" facet and no Mine filter: those are step T.
16. **Bulk bar and Compare.** Shortlist, Reject with a reason picker, and Compare (2 to 4 loaded items, best value per row). "Give to…" waits for step T.
17. **The creator record** is one body used by the peek and the record page. Tabs: Overview (next step with its button, numbers, six latest videos, fit parts with notes, sponsors, addresses, description), Notes and Activity (`log:for`). Emails and Deals wait for steps 6 and 8. Video and channel links are built from checked ids and open through the external-link allowlist.
18. **Notes carry the text they started from.** `creator.notes {id, base, notes}` goes straight through `data:write` (notes aren't in the frame). Main stores `channel_state.notes` and queues `channel.edit notes` with `base` as the base, so a teammate's newer note makes a conflict rather than being overwritten. `''` is stored as null, as the server does. Notes up to 50,000 characters; a longer one pulled from the server arrives cut with `notesCut` and shows read-only, so a save can't drop the rest. (The plan said 5,000.) Esc and Alt+↓ save a note before leaving.

### The email finder and Confirm address

19. **Where an address came from.** Python records, per found address, `{email, source: "about"|"video", videos, business}` in `channels.found_email_sources` (schema 3; `found_emails` stays). `business` means a business word ("business", "inquiries", "collab", "sponsor" and the like) sits within 40 characters before the address. Imported old rows read as `about`, 0 videos, not business. Confidence is pure, in core (`emailConfidence`): About with a business word 0.95; About 0.9; three or more video descriptions 0.8; one or two 0.6; free-mail domains take 0.05 off. Items carry `emails` (up to 10, most sure first).
20. **The finder after a shortlist (live only).** Main waits 2 s after the last shortlist, then queues store-lane `refetch` jobs (at most 50 handles each) for shortlisted creators with no confirmed address. A search is never held up: the finder yields the lane and goes after it. The tray says "Finding emails", then the count found (`find:emails`). Example data never refetches. Addresses are suggestions until a person confirms one.
21. **Confirm address** is undoable (`act`). It sets `email`, `emailConfirmed` and `contactName` and moves `shortlisted` to `contact`. The persister writes `creator.contact` before `creator.stage`. Main stores the primary contact `{method:"email", value, label: name, primary:true, confirmed, source, confidence}`, keeps the other contacts (the old primary stays, `primary:false`), and queues `channel.edit contacts` with the stored JSON as base. An address typed by hand is allowed (source `typed`, confidence null).
22. **Find › Contacts** lists shortlisted creators, those still being looked up last. Each card shows the addresses with source and "N% sure", a name field ("Who reads this inbox?"), Confirm per address and "Type another address". "Confirm all 90%+ (n)" confirms the best address of each card whose best is at least 0.9, in one act, skipping creators already confirmed.

### Gemini keyword ideas

23. **`find:ideas {count}`** builds a topic in main from the five best keywords by kept ratio (at least three found) plus the niche ("AI tools and AI news on YouTube"), and calls the bridge's `action.generate_keywords` with one chat, once per click. The queue's keywords go as `avoid`, not `exclusions`, which would forbid the topics the request is built from. A 60 s gap sits between requests, one at a time (`busy`). With the bridge or add-on off, the answer is `bridge_off`, with a link to Settings › Connections. Example data returns eight fixed AI keywords after 0.9 s and never calls Gemini. Sessions and tests never send a real prompt.

### Toolbox

24. **Toolbox is a screen with route tabs** (`archive`, `never`, `log`), so the URL, palette and G keys work as for Find. Live shows all three. Only built tools are listed. Counts (`toolbox:counts`): Archive is the countdown total, Never contact its total, Activity log the lines since local midnight.
25. **The archive date** is pure, in core: `archiveDate` = `archiveDueAt + (archiveDays − 7)` days (the server's date is always 7), else `rejectedAt + archiveDays` days, else null. A null date is never swept; the list says "No archive date" and Bring back still works.
26. **The countdown list** shows creators at `rejected` not yet archived for good, soonest first, each with the reason, how long ago, a meter and Bring back (an undoable stage change). Below it, **"Archived for good"** lists every tombstone in `channel_archive`, newest first, 50 a page, searchable by handle or name. Each row shows what is kept (see 30).
27. **The sweep** (`main/find/archive-service.ts`). Once 30 s after start, then hourly, and when the Archive tool opens, main picks creators at `rejected` whose archive date has passed and runs store-lane `archive.sweep` (at most 2,000 a job). Python tombstones each with label `rejected`, even a channel with no pipeline row, and the `channel_state` row stays `rejected` (history kept, nothing goes to the server). The sweep re-reads its due list for each job after any wait, since a wait behind a search can last hours. It tries again every 5 s while the lane is busy, gives way when Start is pressed, and folds requests made meanwhile into itself. It runs on live and example data.
28. **Bring back from "Archived for good"** (`toolbox:restore`, up to 50). For a creator at `rejected` the page first restores, then runs the `bringBack` act only if the restore worked. Python removes the tombstone and puts the channel back (see 31). Main waits up to 60 s for the finder or a sweep, but not for a search: the answer is `busy` and the toast says to try again when it pauses. A restore already running is not stopped by Start. A failed job is the value `failed`. On live data main then refetches the handles in the background; example data has none. The record's Bring back does the same when the creator is archived for good, and is disabled while a restore runs.
29. **Never contact tool.** A list of `never` creators with the reason, how long ago and "Allow again" (which asks "Yes, allow emails" or "Keep blocked"), and "Add a channel": search the catalog, write an optional reason, confirm. The act records the reason or "Owner chose never contact". A creator this page blocks shows at the top of the list until main's next catalog build lists it.
30. **Activity log** (`log:page`). The whole local `activity_log`, newest first, 30 a page, hidden and mapped as the frame does (undo markers, the money rule). `log:page` also returns `total`, and `people` (at most 50, most lines first) comes from `peopleInLog`, which returns `{people, total}` in one query. Lines group by local day; a line with a `ref` opens that creator's peek.

### The archive keeps its data

31. **Archiving never makes us know less.** The tombstone keeps every fact a later step reads: name, handle, subscribers, country, first seen, every keyword that found it with its time, uploads in 30 days, latest upload, median views with its basis, the number of videos we had, sponsors and found addresses with sources. `pipeline.db` schema 4 adds the columns to `channel_archive` (`name`, `country`, `videos_last_30`, `latest_upload_at`, `seen_brands`, `found_emails`, `found_email_sources`) and to `channels` (`videos_known`, `unreadable_until`, `read_failures`, `median_known`, `median_known_basis`, `videos_last_30_known`). A file already at version 4 runs the step again on open; every step only adds missing columns. One helper builds the tombstone for every path that archives (the 7-day sweep, the rules' sweep, refetch, the import). Null means never known, never zero.
    *Why:* the owner needs keyword analytics to survive archiving, and the old app lost this data in several ways: no keywords on the sweep, a replace that blanked the row, and a bring back that dropped the keywords. Each one is a test.
32. **Merging.** When a channel already has a tombstone (a re-sweep, a re-find, the import), keywords are a union (earliest time kept), the larger video count wins with its median, and a known text fact beats null. Uploads in 30 days is a window, so a fresher read wins even if smaller.
33. **Restore puts the facts back.** `archive.restore` recreates the `channels` row and the `channel_keywords` rows (original times) in one transaction, then deletes the tombstone. The row has `force_refetch` set and `videos_fetched_at` empty, so it refreshes. The median, its basis and a known 0 uploads are kept in the `*_known` columns, so bringing back and archiving again never says less. The channel shows at once with its last known numbers. The `__manual_refetch__` link is never written into a tombstone and never counted as a keyword that found the channel.
34. **A failed read is not "zero uploads".** A failed upload read raises `ChannelUnreadableError`: the channel stays a candidate, counts a failure in `read_failures`, and steps aside 1, 3, then 7 days (`unreadable_until`). At three failures in a row it leaves the backlog (`READ_GIVE_UP`); a person's refetch or bring back resets the count. Every failed read (keyword, backlog, refetch) is followed by a pause. The backlog keeps the ids it read before a later page failed. Main reads `read_failures >= 3` as `readFailed`. This also ended an old starvation: a channel that always failed filled every slice.
35. **Atomic writes take the lock first.** `_atomic` opens with `BEGIN IMMEDIATE`. The tombstone reads before it writes, and a WAL read-then-write transaction cannot wait for the lock: a parallel search crashed with "database is locked" when a rejected channel was archived (3 in 100 runs under load). A test with two connections proves it now waits.
36. **"Archived for good" shows what is kept:** name (else handle), country, subscribers, median views, uploads in 30 days, and up to three keywords with "+N more" (`keywordsTotal`); unknown reads "not known". Readers tolerate a schema-3 file (missing columns read null).

### Testing

37. **Two tiers.** Each sub-step added at most one light Electron smoke test (`find-triage`, `find-gallery`, `find-contacts`, `toolbox` specs; `find-search` moved onto the runs table). Step 5e added the flow suite: `find-flow.spec.ts` (the prototype's `find_flow.py` items 1, 2, 3, 5 and 6, as steps of one test on one search) and `find-keys.spec.ts` (the triage key matrix and the undo edge cases). Item 4 (Insights) is step 9; item 7 (400 px) is dropped for Windows desktop only. The example channels hold no gold mine (none has a median of 40% of its subscribers), so the flow's facet step uses "Sponsored before" and the channel country; gold is covered by core's unit tests. Python covers the old failure modes (no keywords, blanked rows, 0 for unknown, half-written tombstones). A contracts task that stubs a job adds no test that asserts the stub's failure.

## Consequences

- **Step 6** reads stage `never` in its send gate and takes confirmed contacts (`emailConfirmed`, `contactName`, source and confidence) from creators. Drafts to unconfirmed addresses are its gate to build. The "emailed before" guard grows into the full mail history there.
- **Step T** owns a teammate's run and the overlap warning, handing keywords and creators over, owners on cards, "Who has it", Mine, presence, and R2 sharing. Rows at `new` with no pipeline channel appear then. Python still owns `pipeline.db`.
- **Step 8** adds the record's Deals tab; step 6 adds its Emails tab. (Step 8 was also to add Find › Talent Managers; the owner dropped it on 2026-10-27.)
- **Step 9** writes `FindFilter` from Insights drill-downs, and reads the keyword and discovery data the tombstone now keeps.
- **Step 7** gives prototype mode, which shows the screens live mode hides; the live gate stays as ADR 0016 set it, with `find` now `search`, `triage`, `gallery`, `contacts` and `toolbox` all three tools.
- **The four gaps on hold** (`search-1`, `first-1`, `mail-1`, `mail-2`) were not touched.
- **ADR 0013 §6** says schema version 1; read it as version 4. Writers of new `pipeline.db` columns add them as additive steps and keep a reader that tolerates the older version.
- **Instagram and TikTok** are not in this migration (§9 Q4).

## Known limits and follow-ups

- **The backlog doesn't apply the search rules' bounds.** After the backlog reads a deferred channel, the median and uploads bounds (`minMedianViews`, `minUploads30`) are not applied to it. The old app did the same. The owner decides whether to change it.
- **`record/use-creator-item.ts` repeats part of `useCatalogItem`** (`lib/find-catalog.ts`), to tell a failed load from a missing channel. Fold them together.
- **Promo codes show as sponsors.** "Use code X" counts as a sponsor mention; the ported detector does it on purpose (old behaviour).
- **The heavy-owner timing test** (3,000 channels) checks its bounds only when `CI` is not set, and the bounds are three times the idle targets (1.5 s build, 50 ms query), because the suite runs in parallel. It can still fail on a very busy machine.
- **The first live sweep archives every old reject whose date has passed.** For an owner who imported old data, rejects older than the archive days are tombstoned at once (local pipeline rows only). Each can be brought back from Toolbox › Archive, and nothing is lost.
- **A packaged build** finds neither the add-on folder nor the playbook rule files until step T5; the keyword ideas and Writing rules say so (ADR 0016).
